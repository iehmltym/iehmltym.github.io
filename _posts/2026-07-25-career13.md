# 1.1 什么是互联网（Internet）

互联网（Internet）不是一个软件，而是**全世界大量网络互相连接形成的巨大网络**。

例如：

```text
你的电脑
    │
家庭路由器
    │
运营商
    │
Internet
    │
Google服务器
```

互联网最大的目的只有一个：

> **让两台计算机能够通信。**

但是通信需要解决很多问题。

例如：

* 我不知道对方是谁。
* 我不知道对方在哪里。
* 我不知道怎么把数据送过去。
* 我不知道有没有丢包。
* 我不知道别人会不会偷看。

于是，一项项技术就诞生了。

---

# 1.2 TCP/IP 模型（★★★★★）

SG 不要求你背 OSI 七层，但一定要理解 TCP/IP。

```
应用层（Application）
│
├── HTTP
├── HTTPS
├── SMTP
├── FTP
├── DNS
└── POP3 / IMAP

传输层（Transport）
│
├── TCP
└── UDP

网络层（Internet）
│
└── IP

网络接口层（Link）
│
└── MAC
```

记住一句话：

> **上层使用下层提供的服务。**

例如：

HTTP 不会自己发送数据。

它必须：

```
HTTP
 ↓
TCP
 ↓
IP
 ↓
MAC
 ↓
网线
```

---

# 1.3 IP —— 找到目标计算机（★★★★★）

IP（Internet Protocol Address）就是：

> **网络中的地址。**

例如：

```
8.8.8.8

192.168.1.10

10.0.0.5
```

每台联网设备至少有一个 IP。

作用：

> **告诉数据应该送到哪台计算机。**

例如：

```
你的电脑

↓

203.0.113.5（服务器）
```

如果没有 IP：

数据根本不知道去哪。

---

# 1.4 MAC —— 找到目标网卡（★★★★★）

很多人容易把 IP 和 MAC 混。

实际上：

IP：

> 找电脑。

MAC：

> 找网卡。

例如：

```
Internet

↓

公司网络

↓

某一台电脑

↓

网卡
```

MAC 地址：

```
00-1A-2B-3C-4D-5E
```

每块网卡出厂就有。

考试记一句：

> **IP 是逻辑地址；MAC 是物理地址。**

---

# 1.5 为什么需要 ARP？（★★★★★）

现在：

已经知道：

```
IP：

192.168.1.20
```

但是：

不知道：

```
MAC：

？？？
```

怎么办？

ARP（Address Resolution Protocol）负责：

> **根据 IP 查询 MAC。**

流程：

```
知道 IP
    │
ARP 广播：
"谁是 192.168.1.20？"
    │
目标主机回复：
"我是，我的 MAC 是 xx-xx-xx"
    │
获得 MAC
    │
开始发送数据
```

考试一句话：

> **ARP = IP → MAC。**

---

# 1.6 DNS —— 为什么不用背 IP？（★★★★★）

如果没有 DNS。

你访问 Google：

必须输入：

```
142.250.xxx.xxx
```

根本记不住。

于是：

DNS（Domain Name System）出现。

作用：

> **把域名转换成 IP。**

例如：

```
www.google.com

↓

142.250.xxx.xxx
```

所以：

浏览器真正访问的是：

IP。

不是：

域名。

---

# 1.7 TCP —— 保证可靠通信（★★★★★）

IP：

只负责：

> 尽力送。

它不保证：

* 一定送到
* 顺序正确
* 不重复
* 不丢失

于是：

TCP 出现。

TCP 保证：

* 数据可靠到达
* 按顺序到达
* 丢包重传
* 流量控制
* 拥塞控制

所以：

HTTP、HTTPS、SMTP、FTP 都建立在 TCP 上。

---

# 1.8 UDP —— 更快，但不保证可靠（★★★★★）

UDP：

什么都不保证。

特点：

* 不建立连接
* 不重传
* 不排序
* 延迟低
* 速度快

适合：

* 视频直播
* 在线游戏
* VoIP
* DNS 查询

考试：

TCP = 可靠。

UDP = 快。

---

# 1.9 Port（端口）

IP：

找到电脑。

Port：

找到程序。

例如：

```
192.168.1.10

↓

Chrome（80）

Outlook（25）

SSH（22）
```

服务器通过：

```
IP + Port
```

确定：

到底给哪个程序。

| ----- | --- | ---- |

# 1.11 浏览器访问网页全过程（★★★★★）

假设输入：

```
https://www.google.com
```

实际上发生：

```
① 输入域名

↓

② DNS 查询

↓

⑧ 服务器响应

↓

⑨ 浏览器渲染页面
```

**这张流程图是整本书最重要的一张图。**

* DNS
* TCP
* TLS
* CA
* 数字证书
* AES
* HTTP

都是在这九步里的不同位置。

# 2.1 为什么 HTTP 会出现？

互联网刚诞生的时候，人们只想完成一件事情：

> **让浏览器能够向服务器获取网页。**

于是出现了：

HTTP（HyperText Transfer Protocol）

即：

> **超文本传输协议**

HTTP 本身非常简单。

浏览器：

```text
GET /index.html
```

服务器：

```text
HTTP/1.1 200 OK

<html>......</html>
```

整个过程：

```text
浏览器
    │
HTTP Request
    │
服务器
    │
HTTP Response
    │
浏览器
```

HTTP 只负责：

> 请求（Request）
>
> 响应（Response）

---

# 2.2 HTTP 为什么不安全？

HTTP 最大的问题：

**明文传输（Plain Text）**

例如：

登录：

```text
用户名：admin

密码：123456
```

HTTP：

直接发送：

```text
admin

123456
```

如果有人监听网络：

```text
浏览器

↓

Internet

↓

服务器
```

中间：

```text
黑客
```

他就能直接看到：

```text
账号

密码

聊天内容

银行卡号
```

这就是：

**窃听（Eavesdropping）**

---

## HTTP 三大问题

### ① 数据泄露（Confidentiality）

任何人都能看到。

例如：

```text
密码

聊天内容

订单信息
```

全部都是明文。

---

### ② 数据被修改（Integrity）

例如：

服务器：

本来发送：

```text
价格：

100元
```

中间人：

偷偷改成：

```text
10000元
```

浏览器：

完全不知道。

---

### ③ 身份无法确认（Authentication）

例如：

你输入：

```text
www.bank.com
```

浏览器：

怎么知道：

现在连接的是：

真正银行？

还是：

黑客服务器？

不知道。

所以：

HTTP：

存在三个问题：

```text
不能保密

不能保证完整

不能证明身份
```

---

# 2.3 HTTPS 为什么诞生？

于是：

HTTPS 出现。

很多人以为：

HTTPS 是：

新的协议。

其实不是。

真正关系：

```text
HTTPS

↓

HTTP

+

TLS（SSL）
```

所以：

HTTPS：

其实就是：

> **HTTP + TLS 加密**

HTTP：

负责网页。

TLS：

负责安全。

---

# 2.4 SSL 与 TLS

考试里面：

SSL

TLS

几乎混着说。

实际上：

SSL 是早期版本。

后来：

升级：

变成：

TLS。

今天：

真正使用：

TLS。

但是：

大家仍然习惯说：

SSL证书

SSL连接

SSL加密。

考试：

看到：

SSL

TLS

可以认为：

基本一样。

---

# 2.5 TLS 到底解决什么？

TLS：

一次解决：

HTTP 三个问题。

---

## ① 保密（Confidentiality）

别人：

看不到内容。

例如：

原来：

```text
密码：

123456
```

现在：

变成：

```text
8A F2 6B 13 XX...
```

别人：

看不懂。

---

## ② 完整性（Integrity）

TLS：

会验证：

数据：

有没有被修改。

如果：

黑客：

改：

```text
100

↓

10000
```

浏览器：

立即发现。

连接失败。

---

## ③ 身份认证（Authentication）

浏览器：

必须确认：

现在连接的是：

真正：

Google。

不是：

假的。

于是：

数字证书：

诞生。

---

# 2.6 什么是数字证书（★★★★★）

数字证书：

可以理解成：

> 网站身份证。

例如：

Google：

拥有：

```text
Google 身份证
```

浏览器：

连接：

Google。

第一件事情：

不是：

发送账号。

而是：

先说：

```text
把身份证拿出来。
```

Google：

发送：

数字证书。

浏览器：

检查：

```text
是不是Google？

是不是过期？

是不是假的？

是不是可信机构签发？
```

全部通过。

才继续。

---

# 2.7 数字证书里面有什么？

考试重点：

数字证书：

主要包含：

```text
域名

公钥

签发机构（CA）

有效期

数字签名
```

注意：

考试喜欢考：

> 证书绑定什么？

答案：

**域名（Domain）**

不是：

IP 地址。

所以：

服务器：

今天：

```text
1.1.1.1
```

明天：

```text
2.2.2.2
```

只要：

DNS：

解析正确。

证书：

不用重新申请。

---

# 2.8 CA 是什么？

问题来了。

Google：

自己说：

```text
我是Google。
```

可信吗？

当然：

不可信。

于是：

需要：

第三方。

这个第三方：

就是：

CA（Certificate Authority）

即：

> 数字证书认证机构。

例如：

```text
Google

↓

申请证书

↓

CA审核

↓

CA签名

↓

浏览器信任
```

所以：

浏览器：

真正相信的是：

CA。

不是：

Google 自己。

---

# 2.9 Root CA

浏览器：

为什么相信：

CA？

因为：

浏览器：

出厂：

已经内置：

很多：

Root CA。

例如：

```text
Chrome

↓

Root CA列表

↓

DigiCert

GlobalSign

Let's Encrypt

……
```

浏览器：

收到证书。

第一件事情：

检查：

```text
是不是这些Root CA

签发的。
```

如果：

不是。

浏览器：

立即：

弹出：

```text
你的连接不是私密连接。
```

考试：

最喜欢考：

> 浏览器为什么信任服务器？

答案：

> **因为信任 Root CA。**

---

# 2.10 RSA 为什么出现？

现在：

浏览器：

已经知道：

是真Google。

但是：

还有问题。

AES：

需要：

双方：

拥有：

同一个密钥。

问题：

这个密钥：

怎么发送？

如果：

直接发送：

```text
AES Key
```

黑客：

一样能看到。

于是：

RSA：

出现。

RSA：

负责：

**安全交换 AES 密钥。**

注意：

RSA：

不是：

负责整个网页加密。

考试：

最容易混这里。

---

# 2.11 为什么不用 RSA 加密整个网页？

因为：

RSA：

太慢。

AES：

非常快。

所以：

HTTPS：

真正流程：

```text
RSA

↓

交换AES密钥

↓

AES

↓

加密网页
```

考试：

一句话：

> RSA 负责密钥交换。

> AES 负责真正加密数据。

输入：


# 第三章 TCP、UDP —— 为什么有的网络很可靠，有的网络很快（★★★★★）

> 学完本章，你应该能够回答：
>
> - TCP 和 UDP 到底有什么区别？
> - 为什么 HTTP 一定使用 TCP？
> - 为什么直播、游戏大量使用 UDP？
> - TCP 三次握手为什么存在？
> - 为什么会有四次挥手？
> - 为什么会出现 TIME_WAIT？
> - SG 考试关于 TCP/UDP 的题基本都能做出来。

---

# 3.1 为什么需要 TCP？

上一章我们知道：

IP 可以负责：

> 把数据送到目标计算机。

但是：

IP 并不保证：

```text
一定送到

不会重复

不会丢失

顺序正确
```

例如：

发送：

```text
A

B

C
```

网络可能变成：

```text
A

C

B
```

甚至：

```text
A

C
```

B 丢了。

IP 根本不管。

所以：

必须有人负责：

> "保证数据可靠。"

于是：

TCP（Transmission Control Protocol）

出现。

---

# 3.2 TCP 的作用

TCP 可以理解成：

> **可靠运输公司。**

它负责：

```text
建立连接

保证送达

保证顺序

发现丢包

重新发送

控制速度

避免网络堵塞
```

一句话：

> TCP = Reliable（可靠）

---

# 3.3 UDP 为什么还存在？

很多人第一次学习都会问：

既然 TCP 那么厉害，

为什么还要 UDP？

答案：

因为：

TCP 太慢。

例如：

视频聊天：

如果：

一句话：

```text
你好
```

丢了。

TCP：

```text
重新发送

等待

确认

继续
```

画面：

开始卡。

但是：

视频：

真正需要的是：

流畅。

丢一帧：

根本没人发现。

于是：

UDP：

出现。

---

# 3.4 UDP 的特点

UDP：

什么都不保证。

它只有一句话：

> **我负责发送，收到没有我不管。**

特点：

```text
无连接

没有确认

没有重传

没有排序

速度快

延迟低
```

所以：

UDP：

经常用于：

```text
视频

直播

语音

在线游戏

DNS
```

---

# 3.5 TCP VS UDP（★★★★★）

| TCP | UDP |
|------|------|
| 建立连接 | 不建立连接 |
| 有确认 | 无确认 |
| 保证送达 | 不保证 |
| 有重传 | 无重传 |
| 有顺序 | 无顺序 |
| 较慢 | 很快 |
| 可靠 | 高效率 |

考试：

最喜欢：

问：

哪个：

适合：

视频？

答案：

UDP。

哪个：

适合：

银行转账？

答案：

# 第六章 Firewall（防火墙）—— 企业网络的第一道安全边界（上）

> 本章目标：
>
> 理解 Firewall 的工作原理，而不是死记定义。学完本章后，你应该能够理解企业网络为什么需要 Firewall、不同类型 Firewall 的区别，以及 SG 真题中关于 Firewall、ACL、Stateful Inspection、DMZ、NAT 的所有常见考点。

---

# 6.1 Firewall 为什么会出现

互联网刚出现时，网络中的主机数量很少，大部分计算机之间都可以直接通信。当时的网络环境更加注重"互联互通"，而不是"安全隔离"。

随着互联网的发展，越来越多的服务器暴露在公网，大量攻击开始出现，例如端口扫描、缓冲区溢出、木马传播、蠕虫病毒、DoS 攻击等。如果任何人都可以直接访问企业内部服务器，那么企业网络几乎没有任何安全性。

因此，企业网络开始建立一个明确的安全边界（Security Boundary）。

```text
Internet
      │
      ▼
+----------------+
|    Firewall    |
+----------------+
      │
      ▼
Enterprise Network
```

Firewall 的本质可以理解为企业网络的大门。

所有进入企业网络和离开企业网络的数据，都必须经过 Firewall 检查。

因此，Firewall 的核心职责只有一句话：

> 根据安全策略决定哪些通信允许通过，哪些通信必须拒绝。

注意，这里的对象是**通信（Communication）**，而不是用户。

---

# 6.2 Firewall 与 Router 的区别

很多初学者容易把 Router 和 Firewall 混淆，因为它们通常部署在一起。

实际上，它们解决的是完全不同的问题。

Router 负责回答：

> 数据应该发送到哪里？

Firewall 负责回答：

> 数据是否允许通过？

例如：

```text
Client
   │
Router
   │
Firewall
   │
Server
```

Router 根据路由表（Routing Table）决定下一跳（Next Hop）。

Firewall 根据安全策略（Security Policy）决定是否允许数据通过。

因此：

| 设备 | 主要职责 |
|------|-----------|
| Router | 路由选择 |
| Firewall | 安全过滤 |

考试中如果看到"根据路由表决定数据转发路径"，答案一定不是 Firewall。

---

# 6.3 Firewall 工作在 OSI 哪一层

不同类型 Firewall 工作层次不同。

| Firewall 类型 | OSI 层 |
|--------------|---------|
| Packet Filtering | L3/L4 |
| Stateful Inspection | L3/L4 |
| Circuit-Level Gateway | L5 |
| Application Gateway | L7 |
| WAF | L7（HTTP） |

SG 不要求背 OSI 七层所有功能，但必须知道：

Packet Filtering 只能看到 IP、TCP、UDP 等网络信息。

Application Gateway 可以解析 HTTP、SMTP、FTP 等应用协议。

这也是为什么 Application Gateway 安全性更高，但性能更低。

---

# 6.4 Firewall 到底检查什么

很多人误以为 Firewall 会读取整个网页内容。

实际上，大部分传统 Firewall 首先检查的是数据包头（Packet Header）。

一个 TCP 数据包至少包含下面这些重要信息：

```text
Source IP
Destination IP
Protocol
Source Port
Destination Port
```

Firewall 根据这些字段匹配规则。

例如：

```text
Source IP      192.168.1.10
Destination    203.0.113.8
Protocol       TCP
Source Port    51234
Destination    443
```

Firewall 会逐条检查配置好的安全策略。

例如：

| 条件 | 动作 |
|------|------|
| TCP 80 | Allow |
| TCP 443 | Allow |
| TCP 22 | Deny |
| UDP 53 | Allow |
| Others | Deny |

因此 Firewall 并不是"智能判断"，而是严格按照规则执行。

---

# 6.5 五元组（Five Tuple）

现代 Firewall 最基本的判断依据称为 Five Tuple（五元组）。

包括：

- Source IP（源 IP）
- Destination IP（目标 IP）
- Source Port（源端口）
- Destination Port（目标端口）
- Protocol（协议）

例如：

```text
192.168.1.10
      ↓
203.0.113.8
TCP
51234
443
```

这五项共同决定了一条通信连接。

很多 Stateful Firewall 的连接表（State Table）也是以五元组作为索引建立的。

考试虽然不一定直接出现 Five Tuple 这个名词，但很多题目的本质都是围绕五元组展开。

---

# 6.6 ACL（Access Control List）

Firewall 中最重要的配置就是 ACL。

ACL 全称：

Access Control List。

中文一般翻译为：

访问控制列表。

ACL 就是一张规则表。

例如：

| Rule | Source | Destination | Port | Action |
|------|---------|-------------|------|--------|
| 1 | Any | Web Server | 443 | Allow |
| 2 | Any | Mail Server | 25 | Allow |
| 3 | Any | DB Server | 3306 | Deny |
| 4 | Any | Any | Any | Deny |

Firewall 收到数据后，会按照 ACL 逐条匹配。

第一个满足条件的规则立即生效。

因此：

ACL 的顺序非常重要。

---

# 6.7 First Match Principle（第一匹配原则）

几乎所有 Firewall 都遵循 First Match Principle。

例如：

ACL：

| 顺序 | 条件 | 动作 |
|------|------|------|
| 1 | TCP 443 | Allow |
| 2 | Any | Deny |

浏览器访问 HTTPS：

Destination Port = 443。

Firewall 检查第一条。

满足。

立即允许。

第二条不会继续检查。

再例如：

| 顺序 | 条件 | 动作 |
|------|------|------|
| 1 | Any | Deny |
| 2 | TCP 443 | Allow |

此时：

所有通信都会命中第一条。

HTTPS 永远不会执行第二条。

因此：

ACL 不仅内容重要，顺序同样重要。

这是企业运维中经常出现的问题，也是 SG 偶尔会考查的知识点。

---

# 6.8 Implicit Deny（隐式拒绝）

很多 Firewall 即使没有写最后一条规则，也默认存在：

```text
Deny Any Any
```

这称为：

Implicit Deny。

也就是说：

如果所有规则都没有匹配成功，最终一定拒绝。

例如：

ACL：

| Rule | Port | Action |
|------|------|--------|
| 1 | 80 | Allow |
| 2 | 443 | Allow |

没有写：

```
Others Deny
```

实际上 Firewall 内部仍然会自动执行：

```
Others → Deny
```

因此：

企业通常采用：

> 默认拒绝（Default Deny），按需开放（Allow by Exception）。

这种策略比默认允许更加安全。

---

# 6.9 Default Allow 与 Default Deny

Firewall 存在两种基本设计思想。

## Default Allow

除了明确禁止的内容，其余全部允许。

例如：

```
SSH Deny
Others Allow
```

优点：

部署简单。

缺点：

容易遗漏风险。

安全性较低。

---

## Default Deny

除了明确允许的内容，其余全部拒绝。

例如：

```
HTTPS Allow
DNS Allow
Others Deny
```

优点：

安全性最高。

缺点：

配置工作量较大。

现代企业几乎全部采用：

Default Deny。

考试中如果出现：

> 最小权限原则（Least Privilege）

通常也是 Default Deny 的思想。

---

# 6.10 Stateless Packet Filtering

第一代 Firewall 就是 Packet Filtering。

它最大的特点是：

> 每个数据包独立判断。

例如浏览器访问网站：

```
Client
   │
SYN
   │
Firewall
   │
Server
```

Firewall 检查：

```
TCP
Destination Port = 443
```

符合规则。

允许。

几秒钟后：

服务器返回：

```
ACK
```

Firewall 又重新检查：

```
TCP
Source Port = 443
```

再次匹配 ACL。

注意：

它不知道：

这是刚才建立连接的返回数据。

它只是把每个数据包当成全新的 Packet。

因此称为：

Stateless。

也就是：

没有状态（State）。

---

# 6.11 Stateless Firewall 的问题

由于没有保存连接信息，因此它无法回答一个重要问题：

> 这是正常通信，还是攻击？

例如：

黑客直接向企业电脑发送：

```
TCP
Source Port 443
```

Firewall 会发现：

规则允许 443。

于是：

可能直接放行。

因为它不知道：

这是一个伪造的数据包，还是正常服务器返回的数据。

因此：

Stateless Firewall 安全性有限。

这也是后来 Stateful Inspection 出现的原因。

# 6.12 Stateful Inspection（状态检测防火墙）（★★★★★）

为了解决 Stateless Firewall 无法识别"连接是否合法"的问题，第二代 Firewall 引入了 State（连接状态）的概念，因此称为 Stateful Inspection，也称 Dynamic Packet Filtering。

它最大的特点不是"过滤数据包"，而是"跟踪连接"。

当客户端发起 TCP 三次握手时，Firewall 不仅检查 ACL，还会建立一条连接记录。

例如：

```text
PC
 │
 │ SYN
 ▼
Firewall
 │
 │ 建立 State Table
 ▼
Web Server
```

建立连接后，Firewall 内部会维护一张连接状态表（State Table）。

以后所有属于这个连接的数据包，不需要重新逐条匹配 ACL，而是直接查询 State Table。

因此效率更高，安全性也更高。

---

# 6.13 State Table（状态表）

Stateful Firewall 的核心就是 State Table。

每建立一条 TCP 连接，就会新增一条记录。

例如：

| Source IP | Source Port | Destination IP | Destination Port | Protocol | State |
|------------|-------------|----------------|------------------|----------|-------|
|192.168.1.10|51234|203.0.113.8|443|TCP|ESTABLISHED|

真正的企业级 Firewall 状态表还会保存更多信息，例如：

- TCP Flags
- 建立时间
- 超时时间（Timeout）
- Session ID
- NAT 转换后的地址
- 流量统计
- 数据包数量
- 字节数量

考试不会要求记住这些字段，但一定要知道：

> Stateful Firewall 的本质就是维护一张连接状态表。

---

# 6.14 TCP State Tracking（★★★★★）

为什么 Stateful Firewall 非常适合 TCP？

因为 TCP 本身就是有状态协议。

TCP 三次握手如下：

```text
Client                 Server

SYN  ----------------->

      <------------- SYN+ACK

ACK  ----------------->
```

Firewall 可以完整观察整个过程。

例如：

收到 SYN。

State：

```text
NEW
```

收到 SYN+ACK。

State：

```text
SYN_RECEIVED
```

收到 ACK。

State：

```text
ESTABLISHED
```

以后服务器返回的数据：

Firewall 查询 State Table：

```
ESTABLISHED
```

允许通过。

如果没有对应状态：

立即拒绝。

因此：

Stateful Firewall 与 TCP 的设计天然契合。

---

# 6.15 UDP 为什么也能 Stateful？

很多人会疑惑：

UDP 根本没有建立连接，为什么 Stateful Firewall 还能管理 UDP？

答案是：

Firewall 自己"模拟"连接。

例如：

客户端发送 DNS 查询：

```text
PC
 │
UDP 53
 ▼
DNS
```

Firewall 会创建一条临时状态：

```text
192.168.1.10
↓

8.8.8.8

UDP

Timeout 30 秒
```

如果 30 秒内收到返回数据：

允许。

如果超过 Timeout：

删除状态。

所以：

UDP 的 Stateful 并不是协议本身提供状态，而是 Firewall 自己维护。

这是很多教材容易忽略，但 SG 经常利用来设计干扰项的地方。

---

# 6.16 Stateful Firewall 的优点

相比 Stateless Firewall，Stateful Inspection 具有以下优势：

① 能识别合法连接。

返回的数据包只有属于已经建立连接时才允许进入。

② 自动允许返回流量。

管理员不需要单独配置"返回方向"规则。

③ 能阻止大量伪造数据包。

没有对应连接的数据包通常直接丢弃。

④ ACL 更简单。

很多通信依靠 State Table 即可完成，不需要写大量双向规则。

因此现代企业绝大多数传统 Firewall 都采用 Stateful Inspection。

---

# 6.17 Stateful Firewall 的局限

虽然 Stateful Firewall 比 Stateless 更先进，但仍然存在局限。

第一，它主要工作在第三层、第四层。

它知道：

- IP
- TCP
- UDP
- Port

但是不知道 HTTP 请求内容。

例如：

```http
GET /index.html
```

和

```http
GET /../../etc/passwd
```

对于 Stateful Firewall 来说：

都是 TCP 443。

因此无法识别目录遍历、SQL Injection、XSS 等 Web 攻击。

第二，State Table 会消耗内存。

每建立一个连接，都需要保存状态。

如果攻击者故意建立大量连接，就可能耗尽 Firewall 的资源。

因此后面出现了专门针对 Web 的 WAF。

---

# 6.18 TCP Flags（★★★★★）

Stateful Firewall 判断 TCP 状态时，会参考 TCP Flags。

SG 中最常见的是：

| Flag | 含义 |
|------|------|
| SYN | 建立连接 |
| ACK | 确认 |
| FIN | 正常关闭连接 |
| RST | 强制断开 |
| PSH | 立即交付数据 |
| URG | 紧急数据 |

考试重点只需要掌握：

- SYN：建立连接
- ACK：确认连接
- FIN：正常结束
- RST：异常结束

例如：

黑客发送：

```
ACK
```

但是 Firewall 查询发现：

没有对应连接。

直接拒绝。

---

# 6.19 Session（会话）

很多教材会交替使用 Connection 和 Session。

SG 中一般可以理解为：

Connection 更偏向 TCP 连接。

Session 更偏向 Firewall 维护的一次通信。

例如：

浏览网页。

浏览器可能建立多个 TCP Connection。

Firewall 可以把它们统一管理为多个 Session。

考试一般不会深究二者区别，但看到 Session Table 基本可以理解成 State Table。

---

# 6.20 Timeout（超时机制）

Firewall 不可能永久保存连接。

因此每个 Session 都有 Timeout。

例如：

| 协议 | 常见 Timeout |
|------|--------------|
| TCP Established | 数分钟至数小时 |
| TCP FIN | 数十秒 |
| UDP | 数十秒 |
| ICMP | 数秒 |

如果长时间没有数据：

Firewall 自动删除状态。

否则：

State Table 会无限增长。

---

# 6.21 Anti-Spoofing（★★★★★）

Spoofing 指伪造。

IP Spoofing：

就是伪造源 IP。

例如：

Internet 发来一个数据包：

```
Source IP

192.168.1.20
```

Firewall 一看：

192.168 是企业内网地址。

为什么会从 Internet 来？

明显伪造。

直接拒绝。

这就是：

Anti-Spoofing。

企业 Firewall 通常会检查：

- 私有 IP 是否来自公网
- 本企业地址是否来自公网
- 保留地址是否来自公网

发现异常：

直接丢弃。

考试经常问：

> 防止 IP Spoofing 的设备。

答案通常就是 Firewall。

---

# 6.22 Inbound Filtering 与 Outbound Filtering

Firewall 的规则通常分两个方向。

Inbound：

进入企业。

例如：

```
Internet

↓

Company
```

主要保护企业内部。

Outbound：

离开企业。

例如：

```
Company

↓

Internet
```

主要防止：

- 员工访问危险网站
- 木马向外发送数据
- 数据泄露

现代企业两种都会配置。

---

# 6.23 Egress Filtering

Outbound Filtering 又称：

Egress Filtering。

例如：

公司规定：

禁止员工访问：

```
BT
P2P
赌博网站
```

Firewall 可以直接阻止。

如果企业感染木马。

木马尝试：

```
Command Server
```

Firewall：

拒绝。

因此：

Firewall 不仅保护进入方向，也保护离开方向。

---

# 6.24 Ingress Filtering

Inbound Filtering 又称：

Ingress Filtering。

例如：

Internet：

尝试访问：

```
3389

22

3306
```

Firewall：

全部拒绝。

只开放：

```
443
```

这是最典型的 Ingress Filtering。

---

# 6.25 最小权限原则（Least Privilege）

Firewall 配置遵循最重要的一条安全原则：

Least Privilege。

即：

> 只开放业务真正需要的通信。

例如：

Web Server。

真正需要：

```
443
```

那么：

22

23

21

3306

全部关闭。

开放越少。

攻击面（Attack Surface）越小。

这是 SG 中反复出现的思想，不仅适用于 Firewall，也适用于账号权限、数据库权限、文件权限等所有访问控制场景。

| Stateful Inspection | 记录连接状态 |

# 6.27 Circuit-Level Gateway（电路级网关）

除了 Packet Filtering 和 Stateful Inspection，考试还会出现一种叫 Circuit-Level Gateway（电路级网关）的 Firewall。

很多人第一次看到这个名字容易和 Router 混淆，其实它仍然属于 Firewall，只不过工作层次不同。

Circuit-Level Gateway 工作在 **OSI 第五层（Session Layer，会话层）**，它不关心 HTTP、FTP、SMTP 的具体内容，也不会分析网页数据，而是负责建立和管理通信会话（Session）。

它的核心思想是：

> 不检查通信内容，只检查通信是否建立了合法的 Session。

例如：

```text
Client
   │
TCP Connect
   │
Circuit Gateway
   │
TCP Connect
   │
Server
```

客户端实际上连接的是 Gateway，而不是最终服务器。

Gateway 再重新建立一条 TCP 连接连接服务器，因此客户端和服务器之间不存在直接连接。

这种方式能够隐藏企业内部网络结构，但由于不能检查应用层数据，所以后来逐渐被 Stateful Firewall 和 Proxy 所取代。

---

# 6.28 Application Gateway（应用层网关）

Application Gateway 又称 Proxy Firewall。

它最大的特点就是：

> 可以理解应用协议。

例如 Stateful Firewall 只能看到：

```text
TCP
443
```

而 Application Gateway 能继续解析：

```http
GET /login HTTP/1.1
Host: example.com
Cookie: xxxx
```

或者 SMTP：

```text
MAIL FROM
RCPT TO
DATA
```

或者 FTP：

```text
USER
PASS
PUT
GET
```

因此它能够根据真正的业务内容进行安全检查。

例如：

禁止上传 exe 文件。

禁止访问某些 URL。

禁止下载超过 500MB 的文件。

禁止访问赌博网站。

这些都是普通 Packet Filtering 无法做到的。

---

# 6.29 Application Gateway 的工作方式

Application Gateway 实际上充当了通信双方的代理。

例如：

浏览器访问 Web。

真正过程不是：

```text
Browser
    │
Web Server
```

而是：

```text
Browser
     │
Application Gateway
     │
Web Server
```

因此：

客户端认为自己连接的是 Gateway。

服务器认为自己连接的是 Gateway。

双方并不知道彼此的真实连接。

所以：

Application Gateway 同时具有 Proxy 的特点。

---

# 6.30 为什么安全性更高？

Application Gateway 可以真正分析业务协议。

例如：

HTTP：

```http
GET /admin
```

Firewall 可以根据 URL 判断：

是否允许。

再例如：

HTTP Header：

```http
User-Agent

Cookie

Host
```

都可以分析。

甚至还能限制：

```text
POST

PUT

DELETE
```

这些 HTTP Method。

因此：

它能够发现很多第四层 Firewall 看不到的问题。

---

# 6.31 为什么性能更低？

安全性的提升意味着更多计算。

例如：

Packet Filtering。

只需要读取：

```text
IP

Port

Protocol
```

几十个字节即可。

而 Application Gateway：

需要读取整个 HTTP 请求。

甚至需要解析：

Header

Cookie

Body

URL

Content-Type

Authorization

文件上传内容。

CPU 和内存消耗远高于普通 Firewall。

因此：

安全性最高。

性能最低。

---

# 6.32 Packet Filtering、Stateful、Application Gateway 对比（★★★★★）

| 类型 | 工作层 | 是否记录状态 | 是否解析应用协议 | 性能 | 安全性 |
|------|---------|-------------|----------------|------|--------|
| Packet Filtering | L3/L4 | × | × | ★★★★★ | ★★ |
| Stateful Inspection | L3/L4 | √ | × | ★★★★ | ★★★★ |
| Circuit-Level Gateway | L5 | √ | × | ★★★ | ★★★ |
| Application Gateway | L7 | √ | √ | ★★ | ★★★★★ |

考试经常直接让你比较四者区别。

重点记住：

- Packet Filtering：最快，但能力最弱。
- Stateful：企业最常见。
- Circuit Gateway：检查 Session，不检查应用内容。
- Application Gateway：理解 HTTP、FTP、SMTP 等协议。

---

# 6.33 Firewall Logging（日志）

企业 Firewall 不仅负责阻止攻击，还必须记录日志。

日志主要有三个作用：

**第一，安全审计（Audit）。**

管理员需要知道是谁访问了什么资源。

例如：

```text
2026-07-26

192.168.1.10

Access

Web Server

Allow
```

**第二，事故调查（Forensics）。**

如果服务器被攻击，可以通过 Firewall Log 分析：

- 攻击来自哪个 IP。
- 攻击时间。
- 使用哪个端口。
- 攻击持续多久。
- 是否还有其他攻击源。

**第三，性能分析。**

日志还能统计：

- 带宽使用率。
- 热门服务。
- 异常流量。
- 峰值访问时间。

因此：

Firewall Log 不只是安全用途，也是网络运维的重要数据来源。

---

# 6.34 日志中常见字段

企业 Firewall 日志通常至少包含：

| 字段 | 含义 |
|------|------|
| Timestamp | 时间 |
| Source IP | 源 IP |
| Destination IP | 目标 IP |
| Source Port | 源端口 |
| Destination Port | 目标端口 |
| Protocol | TCP / UDP |
| Action | Allow / Deny |
| Rule ID | 命中的 ACL |
| Bytes | 流量大小 |
| Session ID | 会话编号 |

SG 不要求记忆所有字段，但考试经常问：

> Firewall 日志主要记录哪些内容？

至少要知道：

时间、地址、端口、协议、动作。

---

# 6.35 Firewall 与 NAT 的关系（★★★★★）

很多人认为 NAT 就是 Firewall。

实际上：

NAT 和 Firewall 完全是两个功能。

NAT：

负责地址转换。

Firewall：

负责访问控制。

例如：

```text
192.168.1.10

↓

203.0.113.8
```

这是 NAT。

而：

```text
443 Allow

22 Deny
```

这是 Firewall。

企业 Router 往往同时具有：

```text
Routing

+

NAT

+

Firewall
```

所以很多人误认为它们是一回事。

实际上只是部署在同一设备中。

---

# 6.36 Firewall 与 IDS、IPS 的区别（★★★★★）

考试最喜欢比较这三个设备。

## Firewall

目的：

控制通信。

核心：

Allow / Deny。

不知道攻击是否已经发生。

---

## IDS（Intrusion Detection System）

目的：

发现攻击。

特点：

检测。

报警。

不阻止。

例如：

发现 SQL Injection。

发送告警。

管理员处理。

---

## IPS（Intrusion Prevention System）

IPS 可以理解为：

Firewall + IDS。

发现攻击：

立即阻止。

例如：

检测到：

SQL Injection。

IPS：

直接丢弃数据包。

因此：

| 设备 | 是否阻止 |
|------|---------|
| Firewall | 根据规则阻止 |
| IDS | × |
| IPS | √ |

考试几乎每年都会考。

---

# 6.37 Firewall 与 WAF 的区别（★★★★★）

这是 SG 出现频率最高的比较题之一。

Firewall：

工作对象：

整个网络通信。

例如：

```text
TCP

UDP

ICMP
```

它保护：

企业网络。

WAF：

全称：

Web Application Firewall。

工作对象：

HTTP、HTTPS。

例如：

```http
GET

POST

Cookie

URL

Header
```

它保护：

Web 应用程序。

例如：

SQL Injection。

XSS。

CSRF。

目录遍历。

这些攻击：

Firewall 通常发现不了。

WAF：

专门处理。

因此：

不要把 WAF 当成 Firewall 的升级版。

它们保护对象完全不同。

---

# 6.38 企业网络中的部署位置（★★★★★）

典型部署如下：

```text
                  Internet
                      │
                  Border Router
                      │
                 Firewall
             ┌────────┴────────┐
             │                 │
            DMZ          Internal LAN
             │

            WAF
```

|------|----------|
| Router | 决定数据走哪条路 |
| NAT | 地址转换 |
| Firewall | 控制通信是否允许 |
| Stateful | 记录连接状态 |
| Circuit Gateway | 检查 Session |
| Application Gateway | 理解应用协议 |
| Proxy | 代理客户端 |
| Reverse Proxy | 代理服务器 |
| IDS | 检测攻击，不阻止 |
| IPS | 检测并阻止攻击 |
| WAF | 专门保护 Web 应用 |

---

# 6.40 SG 真题最喜欢考的陷阱

1. 把 Stateful Inspection 和 Application Gateway 混淆。Stateful 能记录连接状态，但不能解析 HTTP 内容；Application Gateway 可以解析应用协议。

2. 把 Firewall 和 NAT 混淆。NAT 负责地址转换，不负责安全控制；Firewall 负责访问控制，不负责 IP 转换。

3. 把 IDS 和 IPS 混淆。IDS 只检测并报警，IPS 检测后立即阻断。

4. 把 Firewall 和 WAF 混淆。Firewall 面向网络通信，WAF 面向 Web 应用攻击。

5. 把 ACL 顺序忽略。Firewall 通常采用 First Match Principle，规则顺序错误会导致后续规则永远无法命中。

6. 忽略 Implicit Deny。企业级 Firewall 通常遵循 Default Deny 策略，未命中的流量默认拒绝。

# 第七章 WAF、IDS、IPS —— 企业网络安全防御体系（★★★★★）

> 本章目标：
>
> 理解 Firewall、WAF、IDS、IPS 的职责边界，掌握 Web 攻击原理及对应防御技术。这一章是 SG 网络安全部分的核心内容，也是考试中最容易混淆的章节之一。

---

# 7.1 为什么需要 WAF？

前一章介绍了 Stateful Firewall。

Stateful Firewall 可以判断：

- IP 地址是否合法
- TCP 是否建立连接
- Port 是否允许访问

但是它不知道 HTTP 请求到底在干什么。

例如：

正常请求：

```http
GET /login HTTP/1.1
```

攻击请求：

```http
GET /login?id=1 OR 1=1
```

对于 Firewall 来说：

两者完全一样。

都是：

```
TCP
443
```

因此：

传统 Firewall 能阻止非法通信，却无法识别合法通信中的恶意内容。

于是出现了：

**WAF（Web Application Firewall）。**

---

# 7.2 WAF 的作用

WAF 全称：

Web Application Firewall。

它保护的对象不是整个网络，而是：

> **Web Application（Web 应用程序）。**

例如：

企业网站：

```text
https://shop.example.com
```

用户登录：

```text
/login
```

商品查询：

```text
/product
```

订单支付：

```text
/payment
```

这些都是 Web Application。

WAF 专门分析：

- URL
- HTTP Header
- Cookie
- Query String
- POST Body
- JSON
- XML

因此：

WAF 工作在 OSI 第七层（Application Layer）。

---

# 7.3 WAF 的部署位置

企业一般采用如下结构：

```text
Internet
     │
Firewall
     │
Reverse Proxy
     │
WAF
     │
Web Server
     │
Database
```

为什么 WAF 放在 Web Server 前面？

因为：

所有 HTTP 请求必须先经过 WAF。

如果发现恶意请求：

立即阻止。

服务器根本收不到攻击数据。

---

# 7.4 WAF 的检测方式

WAF 常见检测方式包括：

**① Signature Detection（特征匹配）**

根据已知攻击特征进行匹配。

例如：

SQL Injection：

```sql
OR 1=1
```

XSS：

```html
<script>
```

目录遍历：

```text
../
```

只要发现这些特征。

立即阻止。

优点：

速度快。

缺点：

无法发现未知攻击。

---

**② Anomaly Detection（异常检测）**

建立正常访问模型。

例如：

正常：

```
URL 长度

100 字符
```

攻击：

```
URL

5000 字符
```

明显异常。

立即报警。

这种方法能够发现未知攻击。

但误报率较高。

---

# 7.5 SQL Injection（★★★★★）

SQL Injection 是 SG 最重要的 Web 攻击。

产生原因：

程序把用户输入直接拼接 SQL。

错误示例：

```sql
SELECT *
FROM user
WHERE id='用户输入'
```

如果用户输入：

```text
1 OR 1=1
```

最终 SQL：

```sql
SELECT *
FROM user
WHERE id='1 OR 1=1'
```

数据库可能返回全部数据。

攻击者可以：

- 登录后台
- 查询数据库
- 删除数据
- 修改数据

因此：

SQL Injection 的本质：

> 用户输入被解释成 SQL 语句。

---

# 7.6 SQL Injection 的防御

真正的解决方案不是 WAF。

而是：

**Prepared Statement（预编译语句）**

例如：

Java：

```java
PreparedStatement
```

Python：

```python
parameterized query
```

.NET：

```text
SqlParameter
```

这样：

用户输入永远只是数据。

不会变成 SQL 语句。

WAF：

只是最后一道防线。

程序本身仍然必须修复。

考试喜欢问：

> SQL Injection 最根本的解决方案是什么？

答案：

参数化查询（Prepared Statement）。

不是 WAF。

---

# 7.7 Cross Site Scripting（XSS）（★★★★★）

XSS：

Cross Site Scripting。

中文：

跨站脚本攻击。

产生原因：

服务器把用户输入直接输出到网页。

例如：

留言板：

用户输入：

```html
<script>
alert(1)
</script>
```

服务器：

直接保存。

其他用户打开页面：

浏览器执行：

```javascript
alert(1)
```

如果攻击代码更复杂：

可以：

- 偷 Cookie
- 劫持 Session
- 假冒用户操作
- 跳转钓鱼网站

因此：

XSS 的本质：

> 浏览器执行了攻击者注入的 JavaScript。

---

# 7.8 XSS 分类

SG 一般了解三种即可。

**Stored XSS**

攻击代码保存到数据库。

以后每个用户都会执行。

例如：

论坛。

留言板。

评论区。

危害最大。

---

**Reflected XSS**

攻击代码存在 URL。

例如：

```
https://example.com?q=<script>
```

服务器立即返回。

浏览器立即执行。

不会保存数据库。

---

**DOM Based XSS**

JavaScript 自己修改 DOM。

服务器甚至不知道发生攻击。

考试出现频率最低。

了解即可。

---

# 7.9 XSS 防御

主要方法：

① Output Encoding（输出转义）

例如：

把：

```html
<
```

转换：

```text
&lt;
```

浏览器就不会执行。

---

② Content Security Policy（CSP）

浏览器规定：

哪些 JavaScript 可以执行。

例如：

只允许：

```
self
```

禁止第三方脚本。

---

③ HttpOnly Cookie

即使发生 XSS。

JavaScript 也无法读取 Cookie。

降低危害。

---

④ 输入验证

过滤危险标签。

例如：

```
<script>

iframe

object
```

但：

输入过滤不是最可靠方案。

输出转义才是根本。

---

# 7.10 CSRF（★★★★★）

CSRF：

Cross Site Request Forgery。

中文：

跨站请求伪造。

很多人和 XSS 混淆。

两者完全不同。

XSS：

攻击浏览器。

CSRF：

利用浏览器。

例如：

用户已经登录：

```
Bank
```

Cookie：

仍然有效。

此时：

攻击者诱导用户访问：

```html
<img src="https://bank.com/transfer?money=10000">
```

浏览器：

自动携带 Cookie。

银行误认为：

用户本人操作。

于是：

转账成功。

攻击者根本不知道 Cookie。

他只是利用了浏览器自动发送 Cookie。

---

# 7.11 CSRF 防御

最常见：

**CSRF Token。**

服务器生成：

随机 Token。

表单提交必须携带。

攻击网站不知道 Token。

因此无法伪造请求。

其他方法：

- SameSite Cookie
- Referer 检查
- Origin 检查
- 二次确认

考试最常出现：

CSRF Token。

必须记住。

---

# 7.12 Directory Traversal（目录遍历）

攻击者利用：

```
../
```

访问服务器文件。

例如：

正常：

```
/image/logo.png
```

攻击：

```
../../etc/passwd
```

如果程序没有检查。

可能读取：

系统配置。

密码文件。

日志文件。

Windows：

可能：

```
..\Windows\System32\
```

防御：

限制访问目录。

路径规范化。

输入验证。

---

# 7.13 File Upload Attack（文件上传攻击）

很多网站允许上传：

头像。

附件。

PDF。

如果服务器：

直接执行上传文件。

攻击者可能上传：

```php
shell.php
```

然后：

浏览器访问：

```
shell.php
```

服务器执行。

完全控制服务器。

因此：

上传文件必须：

- 检查扩展名
- 检查 MIME Type
- 随机文件名
- 上传到不可执行目录

考试偶尔会考。

---

# 7.14 WAF 能防什么？

WAF 最典型保护对象：

| 攻击 | 是否防御 |
|------|---------|
| SQL Injection | √ |
| XSS | √ |
| CSRF | 部分 |
| Directory Traversal | √ |
| File Upload Attack | √ |
| HTTP Flood | √（部分） |

注意：

WAF：

不能解决程序漏洞。

只能缓解攻击。

程序仍然需要修复。

---

# 7.15 IDS（Intrusion Detection System）

IDS：

入侵检测系统。

核心：

> 检测。

不阻止。

例如：

发现：

SQL Injection。

IDS：

记录日志。

发送邮件。

报警。

管理员处理。

因此：

IDS 属于：

Passive Security。

---

# 7.16 IDS 检测方式

Signature Detection：

根据攻击特征。

例如：

已知病毒。

已知 SQL Injection。

速度快。

未知攻击无法发现。

---

Anomaly Detection：

学习正常行为。

发现异常。

能够检测未知攻击。

误报率较高。

现代 IDS：

通常结合两种方式。

---

# 7.17 IPS（Intrusion Prevention System）

IPS：

入侵防御系统。

本质：

IDS + 自动阻止。

流程：

```
收到数据

↓

分析攻击

↓

发现攻击

↓

直接丢弃

↓

记录日志
```

因此：

IPS 工作在线路中。

IDS：

通常旁路部署。

---

# 7.18 Firewall、WAF、IDS、IPS 对比（★★★★★）

| 产品 | 工作对象 | 是否理解 HTTP | 是否阻止 |
|------|----------|--------------|----------|
| Firewall | 网络通信 | × | √ |
| WAF | Web 请求 | √ | √ |
| IDS | 攻击检测 | 可分析 | × |
| IPS | 攻击检测 | 可分析 | √ |

这张表建议直接背下来。

SG 每年几乎都会考其中一种比较题。



# 7.19 Signature Detection（特征检测）（★★★★★）

Signature（特征）可以理解为攻击的"指纹"。

例如：

某种病毒一定会出现：

```text
AB CD EF 12 34
```

某种 SQL Injection 一定包含：

```sql
UNION SELECT
```

某种 WebShell 一定包含：

```php
eval(base64_decode())
```

安全设备提前保存了这些攻击特征。

收到数据后：

流程如下：

```text
收到数据

↓

提取特征

↓

与 Signature Database 比较

↓

命中

↓

报警或阻止
```

这种方式与杀毒软件完全相同。

杀毒软件扫描病毒。

IDS 扫描网络流量。

WAF 扫描 HTTP。

IPS 扫描攻击流量。

本质都是 Signature Matching。

---

# 7.20 Signature Detection 的优缺点

优点：

- 检测速度快。
- 误报率低。
- 已知攻击识别率高。
- 实现简单。

缺点：

- 无法发现未知攻击（Zero-day）。
- Signature 必须不断更新。
- 攻击稍微修改即可绕过。

例如：

数据库已有规则：

```sql
OR 1=1
```

攻击者改成：

```sql
OR/**/1=1
```

如果规则没有更新。

可能绕过检测。

因此企业必须持续更新 Signature Database。

很多安全产品每天都会自动下载最新特征库。

---

# 7.21 Zero-day Attack（零日攻击）

Zero-day（0-Day）指：

> 厂商还不知道漏洞存在，或者还没有发布补丁时，攻击者已经开始利用该漏洞进行攻击。

例如：

今天发现 Windows 新漏洞。

微软：

还没来得及修复。

攻击者：

已经开始攻击。

这种就是：

Zero-day Attack。

由于 Signature Database 中没有该攻击特征。

因此：

传统 Signature Detection 往往无法发现。

---

# 7.22 Anomaly Detection（异常检测）（★★★★★）

为了发现未知攻击。

出现了：

Anomaly Detection。

它的思想完全不同。

不是比较攻击特征。

而是：

> 学习什么叫"正常"。

例如：

企业网站：

每天：

```text
1000 次登录

平均 URL 长度 80 字符

平均 POST 数据 2KB
```

某一天：

突然：

```text
URL 长度

12000 字符
```

或者：

```text
一分钟

登录 100 万次
```

虽然没有任何已知攻击特征。

但是：

明显不正常。

因此：

系统报警。

---

# 7.23 Baseline（基线）

Anomaly Detection 的核心就是：

Baseline。

中文：

基线。

基线就是：

> 系统平时正常运行时的数据。

例如：

CPU：

30%

网络：

200Mbps

登录：

1000 次/小时

这些都是 Baseline。

以后如果：

CPU：

100%

登录：

50 万次。

系统认为：

异常。

---

# 7.24 False Positive（★★★★★）

False Positive：

假阳性。

简称：

FP。

意思：

实际上没有攻击。

系统却认为：

发生攻击。

例如：

双十一。

网站访问人数暴涨。

实际上：

都是正常用户。

IDS：

认为：

DDoS。

开始报警。

这就是：

False Positive。

即：

误报。

---

# 7.25 False Negative（★★★★★）

False Negative：

假阴性。

简称：

FN。

意思：

实际上已经发生攻击。

系统却认为：

没有攻击。

例如：

攻击者：

成功 SQL Injection。

IDS：

没有报警。

攻击成功。

这就是：

False Negative。

即：

漏报。

---

# 7.26 FP 与 FN 的区别（★★★★★）

这是 SG 高频考点。

很多人总是记混。

可以记一句话：

> Positive 表示系统判断"有攻击"；Negative 表示系统判断"没有攻击"。

然后看真假。

| 实际情况 | 系统判断 | 结果 |
|----------|----------|------|
| 没有攻击 | 有攻击 | False Positive |
| 有攻击 | 没有攻击 | False Negative |

一句口诀：

> **误报（FP）：没病说有病。漏报（FN）：有病说没病。**

---

# 7.27 为什么不能完全消除 FP？

如果 IDS 非常敏感。

例如：

任何异常：

都报警。

那么：

漏报（FN）减少。

但是：

误报（FP）增加。

如果 IDS 不敏感。

很多流量：

直接放过。

那么：

误报减少。

漏报增加。

因此：

FP 与 FN 通常存在权衡（Trade-off）。

企业需要根据业务选择平衡点。

---

# 7.28 DoS（Denial of Service）

DoS：

拒绝服务攻击。

目标不是偷数据。

而是：

> 让服务器无法提供正常服务。

例如：

服务器：

每秒只能处理：

1000 个请求。

攻击者：

发送：

100 万请求。

服务器：

CPU：

100%

内存：

100%

正常用户：

无法访问。

攻击成功。

---

# 7.29 DDoS（Distributed Denial of Service）（★★★★★）

DoS：

一台电脑攻击。

DDoS：

大量电脑同时攻击。

例如：

攻击者控制：

100000 台肉鸡（Bot）。

同时访问：

```text
example.com
```

服务器：

瞬间崩溃。

因此：

Distributed：

就是：

分布式。

---

# 7.30 Botnet（僵尸网络）

攻击者：

首先感染大量电脑。

例如：

家庭电脑。

办公电脑。

IoT。

摄像头。

路由器。

感染后：

这些设备：

接受攻击者命令。

统一攻击目标。

这群设备称为：

Botnet。

组成 Botnet 的每一台电脑称为：

Bot（僵尸）。

---

# 7.31 C&C Server（Command & Control）

Bot 不会自己攻击。

真正控制它们的是：

Command & Control Server。

简称：

C&C Server。

攻击流程：

```text
Attacker

↓

C&C Server

↓

Bot1

↓

Bot2

↓

Bot3

↓

Victim
```

攻击者：

只需要控制 C&C。

所有 Bot：

自动执行命令。

---

# 7.32 DoS 与 DDoS 对比

| 项目 | DoS | DDoS |
|------|-----|------|
| 攻击源 | 一台设备 | 大量设备 |
| 流量 | 较小 | 极大 |
| 防御难度 | 较低 | 很高 |
| 是否容易封锁 | 是 | 否 |

为什么 DDoS 更难？

因为：

十万台真实电脑。

全部合法 IP。

Firewall 无法全部封锁。

否则：

正常用户也会被封掉。

---

# 7.33 DDoS 防御

企业常见方法：

① CDN。

攻击流量：

先进入 CDN。

CDN 吸收大量请求。

② Rate Limiting。

限制：

每 IP：

每秒：

100 次请求。

③ Anycast。

多个数据中心：

共同承担流量。

④ DDoS Protection Service。

例如：

Cloudflare。

Akamai。

AWS Shield。

⑤ WAF。

过滤 HTTP Flood。

注意：

普通 Firewall：

无法真正解决大型 DDoS。

因为：

带宽已经被占满。

Firewall 根本来不及处理。

---

# 7.34 Security Defense in Depth（纵深防御）（★★★★★）

企业不会依赖一个设备。

而是：

多层防御。

例如：

```text
Internet

↓

Router

↓

Firewall

↓

IPS

↓

Reverse Proxy

↓

WAF

↓

Application

↓

Database Encryption

↓

Backup

↓

SIEM
```

即使：

Firewall 被绕过。

还有：

IPS。

IPS 被绕过。

还有：

WAF。

程序出现漏洞。

还有：

数据库权限控制。

这就是：

Defense in Depth。

中文：

纵深防御。

也是 SG 非常喜欢考的安全思想。

---

# 7.35 单点防御为什么危险？

如果企业只有 Firewall：

```text
Internet

↓

Firewall

↓

Database
```

Firewall 一旦失效。

数据库：

直接暴露。

因此：

现代安全设计强调：

**不要相信任何单一安全设备。**

每一层都假设上一层可能已经失效。

这就是 Zero Trust 和 Defense in Depth 的设计思想基础。




# 7.36 Defense in Depth（纵深防御）与 Zero Trust（零信任）的区别（★★★★★）

很多教材都会同时介绍 Defense in Depth（纵深防御）和 Zero Trust（零信任），不少人容易认为它们是一回事，其实它们解决的问题不同。

**Defense in Depth（纵深防御）回答的是：**

> 如果第一道防线失效怎么办？

答案是继续依赖第二道、第三道、第四道防线。

例如：

```text
Internet
    │
Firewall
    │
IPS
    │
WAF
    │
Application
    │
Database
```

攻击者即使突破 Firewall，仍然要面对 IPS；绕过 IPS，还需要绕过 WAF；进入应用系统后，还要受到数据库权限控制和加密保护。

因此，纵深防御强调的是**多层安全控制**。

---

Zero Trust（零信任）回答的是另一个问题：

> 为什么要默认相信内部网络？

传统企业网络认为：

```text
Internet：危险
Internal：可信
```

所以很多服务器之间几乎没有限制。

Zero Trust 的理念完全相反：

> **任何访问都不默认可信，无论来自外部还是内部，都必须重新验证身份和权限。**

因此 Zero Trust 更关注：

- 身份认证（Authentication）
- 权限控制（Authorization）
- 持续验证（Continuous Verification）
- 最小权限（Least Privilege）

所以两者关系可以总结为：

| 名称 | 核心思想 |
|------|----------|
| Defense in Depth | 多层安全设备，层层防御 |
| Zero Trust | 不默认信任任何用户、任何设备、任何网络 |

---

# 7.37 Security Control（安全控制）

ISO 27001、ISMS 和 SG 考试中经常出现 Security Control（安全控制）这个词。

Security Control 指的是为了降低风险而采取的各种措施，它不仅仅包括 Firewall、WAF 等设备，也包括制度、流程和人员管理。

例如：

技术控制（Technical Control）：

- Firewall
- IDS
- IPS
- WAF
- VPN
- MFA

管理控制（Administrative Control）：

- 安全制度
- 操作规范
- 权限审批
- 安全教育
- 审计制度

物理控制（Physical Control）：

- 门禁系统
- 摄像头
- 机房锁
- 保安
- 指纹识别

考试经常问：

> Firewall 属于哪种安全控制？

答案：

**Technical Control（技术控制）**。

---

# 7.38 Preventive、Detective、Corrective Control（★★★★★）

安全控制还可以按照作用进行分类。

## Preventive Control（预防性控制）

作用是在攻击发生之前进行预防。

例如：

- Firewall
- WAF
- MFA
- 门禁系统
- 密码策略
- 权限控制

特点：

攻击最好不要发生。

---

## Detective Control（检测性控制）

攻击已经发生，但能够及时发现。

例如：

- IDS
- SIEM
- 日志分析
- 监控系统
- 安全告警

特点：

不能阻止攻击，但能够尽快发现。

---

## Corrective Control（纠正性控制）

攻击已经造成影响，需要恢复业务。

例如：

- 数据恢复
- Backup
- Disaster Recovery
- 系统重建
- 漏洞修复

特点：

降低损失，恢复正常运行。

---

考试最喜欢让你判断属于哪一类。

| 控制措施 | 类型 |
|----------|------|
| Firewall | Preventive |
| WAF | Preventive |
| IDS | Detective |
| 日志审计 | Detective |
| 数据恢复 | Corrective |
| Backup | Corrective |

---

# 7.39 Kill Chain（攻击链）

现代攻击通常不是一步完成，而是多个阶段连续进行。

典型攻击流程如下：

```text
信息收集
    ↓
漏洞扫描
    ↓
漏洞利用
    ↓
权限提升
    ↓
横向移动
    ↓
数据窃取
    ↓
清除痕迹
```

这就是攻击链（Kill Chain）。

企业的目标不是一定要阻止所有攻击，而是在攻击链中的任意一个阶段发现并阻止攻击。

例如：

- Firewall 阻止漏洞利用。
- IDS 发现异常流量。
- WAF 阻止 SQL Injection。
- SIEM 发现异常登录。
- EDR 阻止恶意程序运行。

攻击链只要有一个环节失败，整个攻击就可能失败。

---

# 7.40 Attack Surface（攻击面）

Attack Surface（攻击面）表示攻击者可以利用的入口数量。

例如：

服务器开放：

```text
22
80
443
3306
3389
21
23
25
110
143
5900
8080
```

攻击面非常大。

如果真正业务只需要：

```text
443
```

那么关闭其余端口后：

```text
443
```

攻击面明显减小。

因此企业经常强调：

- 关闭不用的端口。
- 删除不用的软件。
- 停止不用的服务。
- 禁止默认账号。
- 删除测试页面。

这些都是为了减少 Attack Surface。

Attack Surface 越小，被攻击的可能性越低。

---

# 7.41 Hardening（系统加固）（★★★★★）

Hardening（加固）就是通过各种配置降低系统被攻击的风险。

服务器安装完成后，并不能直接投入生产环境，而是需要进行安全加固。

典型措施包括：

- 删除默认账户。
- 修改默认密码。
- 禁止 Root 远程登录。
- 关闭不必要的端口。
- 删除测试程序。
- 安装最新安全补丁。
- 启用日志记录。
- 配置 Firewall。
- 配置最小权限。
- 禁止匿名访问。

可以发现，Hardening 本身不是一种产品，而是一系列安全配置工作的总称。

考试中如果出现"服务器加固"、"安全加固"，通常指的就是这些内容。

---

# 7.42 Patch Management（补丁管理）（★★★★★）

绝大多数攻击利用的都是已经公开的漏洞，因此及时安装安全补丁是最重要的防御措施之一。

补丁管理通常包括以下流程：

```text
漏洞公开
      ↓
厂商发布补丁
      ↓
测试环境验证
      ↓
评估业务影响
      ↓
正式环境部署
      ↓
确认安装成功
```

很多企业不会第一时间直接升级生产环境，而是先在测试环境验证，避免补丁影响业务系统。

考试中经常会问：

> 为什么补丁不能直接安装到生产环境？

因为补丁可能导致：

- 系统无法启动。
- 程序兼容性问题。
- 第三方软件异常。
- 业务中断。

因此必须先测试，再部署。

---

# 7.43 Vulnerability（漏洞）与 Threat（威胁）与 Risk（风险）（★★★★★）

这是 ISMS、SG 最经典的一组概念，也是很多人最容易混淆的地方。

**Vulnerability（漏洞）**：系统本身存在的弱点。例如程序存在 SQL Injection、服务器没有安装补丁、密码过于简单。

**Threat（威胁）**：可能利用漏洞造成损害的人或事件。例如黑客、病毒、勒索软件、地震、火灾。

**Risk（风险）**：威胁利用漏洞后，对业务造成损失的可能性。

三者之间的关系可以理解为：

```text
Threat
    │
利用
    ▼
Vulnerability
    │
产生
    ▼
Risk
```

没有漏洞，威胁很难成功；没有威胁，漏洞暂时不会造成损失；只有两者结合，才真正形成风险。

因此，安全工作的目标就是：

- 减少漏洞（Patch、Hardening）。
- 降低威胁（Firewall、WAF、IDS）。
- 降低风险（Backup、BCP、监控、应急响应）。

这一组概念几乎每年都会在 SG 或 ISMS 中出现，必须彻底理解，而不是死记定义。

# 7.44 Vulnerability Management（漏洞管理）（★★★★★）

发现漏洞只是第一步，真正重要的是持续管理漏洞。

企业中的漏洞管理通常遵循以下流程：

```text
资产识别
    ↓
漏洞扫描
    ↓
风险评估
    ↓
制定修复计划
    ↓
安装补丁
    ↓
验证修复结果
    ↓
持续监控
```

很多初学者认为：

> 发现漏洞 = 完成安全工作。

实际上完全不是。

真正重要的是：

- 是否已经修复？
- 是否还有同类漏洞？
- 是否影响业务？
- 是否需要临时缓解措施？

因此，漏洞管理是一个持续循环（Continuous Process），而不是一次性工作。

---

# 7.45 Vulnerability Scanner（漏洞扫描器）

漏洞扫描器用于自动检查系统是否存在已知漏洞。

常见检查内容包括：

- 是否安装最新补丁。
- 是否存在默认账号。
- 是否开放危险端口。
- 是否使用弱密码。
- 是否存在已知 CVE。
- 是否使用过期软件版本。
- SSL/TLS 配置是否安全。

扫描结束后通常会生成报告，例如：

| 漏洞 | 风险等级 |
|------|----------|
| Apache 版本过旧 | High |
| TLS1.0 已启用 | Medium |
| FTP 匿名登录 | High |
| HTTP Server Banner 暴露 | Low |

管理员根据风险等级安排修复。

需要注意：

> 漏洞扫描器只能发现漏洞，不能自动修复漏洞。

---

# 7.46 CVE（Common Vulnerabilities and Exposures）

几乎所有公开漏洞都有一个唯一编号：

CVE。

例如：

```text
CVE-2021-44228
```

这是著名的：

Log4Shell 漏洞。

编号格式通常为：

```text
CVE-年份-编号
```

例如：

```text
CVE-2024-12345
```

有了 CVE 编号，全世界都知道讨论的是同一个漏洞。

因此：

安全公告、补丁说明、漏洞数据库都会引用 CVE。

考试一般不会要求记编号，但要知道：

> CVE 是公开漏洞编号。

---

# 7.47 CVSS（Common Vulnerability Scoring System）（★★★★★）

发现漏洞以后，需要评估：

> 这个漏洞到底有多危险？

于是出现：

CVSS。

CVSS 用于评价漏洞危险程度。

评分范围：

```text
0.0 ～ 10.0
```

一般分为：

| 分数 | 等级 |
|------|------|
| 0.0 | None |
| 0.1～3.9 | Low |
| 4.0～6.9 | Medium |
| 7.0～8.9 | High |
| 9.0～10.0 | Critical |

例如：

某漏洞：

```
CVSS：9.8
```

说明：

极高风险。

需要立即修复。

而：

```
CVSS：2.1
```

说明：

风险较低。

可以安排后续维护。

注意：

CVSS 评价的是：

**漏洞本身的危险程度。**

不是企业最终风险。

---

# 7.48 Risk Assessment（风险评估）

企业不会因为发现漏洞就立刻停机修复。

还需要考虑：

- 是否真的容易被利用？
- 是否暴露互联网？
- 是否有补偿措施？
- 是否影响核心业务？

例如：

同一个漏洞：

开发测试服务器：

风险：

Medium。

互联网银行服务器：

风险：

Critical。

因此：

真正管理的是：

Business Risk。

而不仅仅是 CVSS。

---

# 7.49 Risk Treatment（风险处理）（★★★★★）

ISMS 中最经典的问题之一。

发现风险以后：

企业通常有四种处理方式。

---

## ① Risk Reduction（降低风险）

最常见。

例如：

安装补丁。

启用 Firewall。

修改密码。

部署 MFA。

降低攻击成功率。

---

## ② Risk Avoidance（回避风险）

直接取消业务。

例如：

FTP 风险太高。

企业决定：

停止 FTP 服务。

风险自然消失。

---

## ③ Risk Transfer（转移风险）

将风险转给第三方。

例如：

购买网络安全保险。

使用云安全服务。

委托专业安全运营。

风险没有消失。

只是承担者发生变化。

---

## ④ Risk Acceptance（接受风险）

企业认为：

修复成本远高于风险。

于是：

接受风险。

例如：

内部测试服务器。

没有公网访问。

影响极小。

暂不修复。

考试最喜欢考四种处理方式。

必须能够区分。

---

# 7.50 Penetration Test（渗透测试）（★★★★★）

漏洞扫描：

告诉你：

"可能有漏洞。"

渗透测试：

真正尝试攻击。

例如：

扫描器：

提示：

```
Apache 版本可能存在漏洞
```

渗透测试：

真的利用漏洞。

获得服务器权限。

因此：

两者区别如下：

| 项目 | 漏洞扫描 | 渗透测试 |
|------|----------|----------|
| 是否主动攻击 | 否 | 是 |
| 是否利用漏洞 | 否 | 是 |
| 自动化程度 | 高 | 较低 |
| 人工参与 | 少 | 多 |

漏洞扫描属于：

发现问题。

渗透测试属于：

验证问题。

---

# 7.51 Security Audit（安全审计）

Security Audit 的目的不是发现漏洞。

而是：

检查安全制度是否得到执行。

例如：

检查：

- 是否按照规定修改密码？
- 是否定期备份？
- 是否记录日志？
- 是否按照流程审批权限？
- 是否遵守 ISMS？

因此：

Audit 更关注：

**Compliance（合规性）。**

而不是：

技术漏洞。

---

# 7.52 Compliance（合规）

Compliance 指：

遵守法律、标准、制度。

例如：

企业必须遵守：

- ISO27001
- ISMS
- GDPR
- 日本个人信息保护法
- 公司内部制度

没有遵守：

就是：

Non-compliance。

考试喜欢问：

安全审计主要目的是什么？

答案通常不是：

提高性能。

而是：

确认是否符合安全要求。

---

# 7.53 Security Policy（安全策略）

所有技术设备最终都来源于：

Security Policy。

例如：

公司规定：

```
禁止 USB。

必须 MFA。

密码至少 12 位。

禁止访问赌博网站。
```

这些都是：

Security Policy。

Firewall：

只是执行策略。

WAF：

只是执行策略。

真正决定：

"应该怎么做"的是：

Security Policy。

---

# 7.54 Policy、Standard、Procedure 的区别（★★★★★）

这是 ISMS 高频考点。

很多人完全混淆。

Policy：

规定：

**做什么（What）**

例如：

```
所有员工必须使用 MFA。
```

---

Standard：

规定：

**做到什么标准（Requirement）**

例如：

```
密码长度不少于 12 位。

至少包含大小写和数字。
```

---

Procedure：

规定：

**具体怎么做（How）**

例如：

```
打开系统设置。

点击修改密码。

输入新密码。

确认保存。
```

总结：

| 名称 | 作用 |
|------|------|
| Policy | 方向、原则 |
| Standard | 技术标准 |
| Procedure | 操作步骤 |

考试非常喜欢比较三者。

---

# 7.55 Security Awareness（安全意识）

很多攻击并不是技术漏洞造成，而是人员问题。

例如：

员工：

点击钓鱼邮件。

泄露密码。

连接陌生 USB。

共享账号。

因此：

企业必须开展：

Security Awareness Training（安全意识培训）。

培训内容通常包括：

- 钓鱼邮件识别。
- 社会工程学。
- 密码管理。
- 信息分类。
- 移动设备安全。
- USB 使用规范。
- 办公桌清理（Clean Desk）。

很多企业每年都会进行一次安全教育。

这是 ISMS 的基本要求之一。

---

# 7.56 Social Engineering（社会工程学）（★★★★★）

社会工程学不是破解计算机。

而是：

利用人的心理。

例如：

攻击者假装：

- IT 管理员。
- 快递员。
- 银行工作人员。
- 公司领导。
- 同事。

诱导用户：

- 告诉密码。
- 点击链接。
- 打开附件。
- 转账。
- 提供验证码。

攻击的对象不是系统，而是：

**人。**

因此：

很多时候：

企业最薄弱的安全环节不是 Firewall，而是员工本身。

考试中如果出现：

"利用人的信任心理骗取信息"

答案通常就是：

Social Engineering。


# 第七章（续） 身份认证（Authentication）与访问控制（Access Control）

前面介绍了 Firewall、WAF、IDS、IPS 等安全设备，它们主要负责保护网络和系统。而真正决定"谁可以访问系统"的是身份认证（Authentication）和访问控制（Access Control）。

在企业安全体系中，这部分内容的重要性并不低于网络安全，也是 SG 考试的重点。

---

# 7.57 Authentication（身份认证）（★★★★★）

Authentication（认证）回答的问题只有一个：

> **你是谁？**

例如：

员工登录公司 OA 系统。

系统首先需要确认：

- 是否真的是张三？
- 是否真的是管理员？
- 是否真的是数据库管理员？

只有身份确认成功，系统才会进入下一步。

身份认证与权限没有关系。

例如：

```text
用户名：admin
密码：123456
```

系统确认：

确实是 admin。

认证成功。

但是：

admin 能不能删除数据库？

这不是 Authentication 决定，而是 Authorization（授权）决定。

因此：

> Authentication = 确认身份。

---

# 7.58 Authorization（授权）（★★★★★）

Authorization 回答的问题是：

> **你可以做什么？**

例如：

同样登录 ERP 系统。

管理员：

可以新增用户。

普通员工：

只能查看工资。

财务：

可以导出报表。

虽然三个人都已经完成 Authentication，但每个人拥有的权限完全不同。

因此：

| 概念 | 回答的问题 |
|------|------------|
| Authentication | 你是谁？ |
| Authorization | 你能做什么？ |

这是 SG 最经典的概念题之一。

---

# 7.59 Authentication 与 Authorization 的关系

它们的执行顺序不能颠倒。

必须先认证，再授权。

流程如下：

```text
用户登录
    │
    ▼
Authentication
（确认身份）
    │
    ▼
Authorization
（检查权限）
    │
    ▼
允许访问资源
```

如果连身份都没有确认，就谈不上权限。

因此考试中如果出现：

> "根据用户身份决定允许访问哪些资源"

其中：

确认身份属于 Authentication。

决定访问范围属于 Authorization。

---

# 7.60 三种认证要素（Authentication Factors）（★★★★★）

身份认证通常依赖三种认证要素（Authentication Factors）。

## ① Something You Know（你知道的）

例如：

- 密码（Password）
- PIN
- 安全问题

特点：

依赖记忆。

最容易泄露。

---

## ② Something You Have（你拥有的）

例如：

- 手机
- IC 卡
- USB Token
- OTP 设备
- 员工门禁卡

特点：

依赖实体设备。

别人即使知道密码，也需要拿到设备。

---

## ③ Something You Are（你本人的特征）

例如：

- 指纹
- 人脸
- 虹膜
- 静脉
- 声纹

特点：

属于生物特征认证（Biometric Authentication）。

不容易遗忘，但也不能像密码一样随意更换。

---

考试非常喜欢判断认证方式属于哪一种。

例如：

| 认证方式 | 类型 |
|----------|------|
| Password | Something You Know |
| IC Card | Something You Have |
| Fingerprint | Something You Are |

---

# 7.61 Multi-Factor Authentication（MFA）（★★★★★）

MFA（多因素认证）指：

> **同时使用两种或以上不同类型的认证要素。**

注意：

重点是：

**不同类型。**

例如：

密码 + 手机验证码

```text
Password

+

SMS Code
```

Password 属于：

Something You Know。

手机验证码属于：

Something You Have。

因此：

属于 MFA。

---

再例如：

密码 + 密码提示问题。

两者都属于：

Something You Know。

因此：

**不是 MFA。**

这是考试最喜欢设置的陷阱。

---

# 7.62 One-Time Password（OTP）

OTP：

一次性密码。

顾名思义：

每个密码只能使用一次。

常见形式包括：

- 手机短信验证码。
- Google Authenticator。
- Microsoft Authenticator。
- 硬件 Token。

例如：

登录银行：

输入密码后：

系统要求：

```
348291
```

30 秒后：

自动失效。

即使攻击者偷到验证码，也无法再次使用。

因此 OTP 可以有效降低密码泄露后的风险。

---

# 7.63 Password（密码）

密码仍然是最普遍的认证方式。

优秀密码通常具有以下特点：

- 长度足够。
- 包含大小写字母。
- 包含数字。
- 包含特殊字符。
- 不使用生日。
- 不使用姓名。
- 不重复使用。

例如：

```
P@ssw0rd123
```

虽然复杂，但如果很多网站都使用同一个密码，一旦其中一个网站泄露，其余网站也会受到影响。

因此企业通常要求：

> 不同系统使用不同密码。

---

# 7.64 Password Policy（密码策略）

企业通常制定统一密码策略。

例如：

| 项目 | 要求 |
|------|------|
| 最小长度 | 12 位 |
| 大小写 | 必须包含 |
| 数字 | 必须包含 |
| 特殊字符 | 必须包含 |
| 历史密码 | 不允许重复最近 5 次 |
| 有效期 | 90 天 |

这些规定属于 Password Policy。

Firewall 无法实现这些要求。

通常由操作系统、Active Directory 或 IAM 系统负责执行。

---

# 7.65 Brute Force Attack（暴力破解）（★★★★★）

Brute Force（暴力破解）就是不断尝试密码。

例如：

攻击程序自动尝试：

```text
123456
12345678
password
admin
qwerty
...
```

直到登录成功。

如果密码足够简单，很容易被破解。

因此企业通常采用以下措施进行防御：

- 密码复杂度要求。
- 登录失败次数限制。
- 登录延迟（Delay）。
- CAPTCHA（验证码）。
- MFA。

---

# 7.66 Dictionary Attack（字典攻击）

Dictionary Attack 与 Brute Force 很像，但效率更高。

Brute Force：

所有组合全部尝试。

例如：

```
aaaa

aaab

aaac
```

一直尝试下去。

Dictionary Attack：

只尝试人们最常使用的密码。

例如：

```
123456

password

admin

qwerty

welcome
```

因为现实中很多用户喜欢使用简单密码，所以字典攻击的成功率往往很高。

---

# 7.67 Account Lockout（账户锁定）

为了防止暴力破解，企业通常会配置账户锁定策略。

例如：

连续输入错误密码：

5 次。

系统：

自动锁定：

30 分钟。

这样攻击者无法无限尝试密码。

但是锁定时间也不能太长，否则正常用户输错密码后会影响工作。

因此企业需要在安全性和可用性之间进行平衡。

---

# 7.68 CAPTCHA（验证码）

CAPTCHA 的主要作用不是防止黑客，而是区分：

> **访问者是真人还是程序。**

例如：

登录页面要求：

- 点击图片。
- 识别红绿灯。
- 输入图片文字。

机器人很难自动完成。

因此可以有效减少：

- 暴力破解。
- 自动注册。
- 恶意刷票。
- 垃圾评论。

需要注意：

CAPTCHA 不能代替密码，它只是增加攻击成本。

---

# 7.69 Single Sign-On（SSO）（★★★★★）

SSO（单点登录）是现代企业广泛使用的身份认证技术。

传统方式：

每个系统都需要重新登录。

例如：

```text
OA → 登录

ERP → 登录

邮件 → 登录

考勤 → 登录
```

员工每天需要输入很多次密码。

SSO 的思想是：

> **登录一次，访问多个系统。**

流程如下：

```text
用户登录
      │
      ▼
Identity Provider
      │
      ├────► OA
      ├────► ERP
      ├────► Mail
      └────► HR
```

系统之间互相信任认证结果，因此用户无需重复输入密码。

SSO 提高了用户体验，也方便企业统一管理身份。

不过，一旦 SSO 身份被盗，攻击者可能同时访问多个系统，因此通常会结合 MFA 一起使用。

# 7.70 Identity Provider（IdP）（★★★★★）

上一节介绍了 SSO（Single Sign-On），那么是谁负责验证用户身份，并告诉其他系统"这个用户已经登录"呢？

答案就是：

**Identity Provider（IdP，身份提供者）。**

IdP 可以理解为企业统一的身份认证中心。

例如：

```text
            +------------------+
            | Identity Provider|
            +------------------+
              │    │    │    │
              ▼    ▼    ▼    ▼
             OA   ERP Mail HR
```

员工只需要向 IdP 登录一次。

IdP 验证身份成功后，会向其他系统发送认证结果。

其他系统相信 IdP，因此无需再次输入用户名和密码。

企业常见的 IdP 包括：

- Microsoft Entra ID（原 Azure AD）
- Okta
- Keycloak
- Google Identity
- Ping Identity

SG 考试一般不会要求记忆具体产品，但要理解 IdP 的职责。

---

# 7.71 Service Provider（SP）

与 IdP 对应的是：

**Service Provider（SP，服务提供者）。**

SP 指真正提供业务功能的系统。

例如：

- OA 系统
- ERP 系统
- 邮件系统
- CRM
- 人事系统

它们负责业务处理，而不是身份认证。

整个流程如下：

```text
用户
 │
 ▼
Identity Provider（认证）
 │
 ▼
Service Provider（提供业务）
```

因此：

- IdP 负责"你是谁"。
- SP 负责"你可以使用什么服务"。

---

# 7.72 SAML（★★★★★）

企业 SSO 最经典的协议之一就是：

**SAML（Security Assertion Markup Language）。**

SAML 是一种身份认证协议。

它不是登录系统。

不是数据库。

也不是服务器。

它规定：

> IdP 如何把认证结果发送给 SP。

例如：

员工访问 ERP。

ERP 发现：

没有登录。

于是：

跳转到 IdP。

IdP 登录成功。

返回：

```
Authentication Assertion
```

ERP：

验证 Assertion。

允许登录。

整个过程如下：

```text
User
 │
 ▼
ERP（SP）
 │
 ▼
IdP
 │
登录成功
 │
▼
SAML Assertion
 │
▼
ERP
```

因此：

SAML 的核心作用就是：

**传递认证信息。**

---

# 7.73 OAuth（★★★★★）

很多人第一次学习 OAuth 时都会误认为：

OAuth 就是登录。

实际上：

OAuth 解决的问题完全不同。

OAuth 回答的是：

> **是否允许第三方访问我的资源？**

例如：

你使用 GitHub 登录一个网站。

真正过程不是：

网站知道你的 GitHub 密码。

而是：

GitHub 询问：

```
是否允许该网站读取你的资料？
```

如果同意。

GitHub：

发放：

Access Token。

第三方网站：

以后使用 Token 获取资料。

整个过程中：

第三方网站永远不知道你的 GitHub 密码。

因此：

OAuth 本质上是：

**授权（Authorization）协议。**

不是认证协议。

这是考试最喜欢出的概念题。

---

# 7.74 OAuth 工作流程（理解即可）

典型流程如下：

```text
User
 │
 ▼
Third Party App
 │
 ▼
GitHub
 │
用户同意授权
 │
▼
Access Token
 │
▼
Third Party App
 │
▼
读取用户资料
```

注意：

整个过程中：

密码始终保存在 GitHub。

第三方网站只拿到：

Access Token。

---

# 7.75 OpenID Connect（OIDC）（★★★★★）

既然 OAuth 主要负责授权。

那么：

如何实现登录？

于是出现：

OpenID Connect（OIDC）。

OIDC 可以理解为：

> **OAuth + 身份认证。**

OAuth：

告诉别人：

```
允许访问哪些资源。
```

OIDC：

进一步告诉别人：

```
这个用户是谁。
```

因此：

现代互联网登录大量采用：

OpenID Connect。

例如：

- Google 登录。
- Microsoft 登录。
- Apple 登录。
- LINE 登录。

考试中常见比较：

| 协议 | 主要用途 |
|------|----------|
| SAML | 企业 SSO |
| OAuth | 授权 |
| OpenID Connect | 身份认证 + OAuth |

---

# 7.76 Access Token（访问令牌）

Token 可以理解为：

**临时通行证。**

例如：

登录成功后：

服务器生成：

```
eyJhbGciOi...
```

以后访问：

浏览器：

发送：

```
Authorization: Bearer Token
```

服务器：

验证 Token。

如果合法。

允许访问。

因此：

很多现代系统已经不再每次发送用户名和密码。

而是：

发送 Token。

---

# 7.77 Session 与 Token 的区别（★★★★★）

很多人容易把 Session 和 Token 混淆。

Session：

状态保存在服务器。

例如：

```text
User

↓

Server

↓

Session Table
```

服务器需要保存：

每个用户的 Session。

用户浏览器：

只保存：

Session ID。

---

Token：

状态主要保存在客户端。

服务器通常只验证 Token 是否合法。

例如：

```text
User

↓

Token

↓

Server
```

服务器不一定保存每个用户状态。

因此：

现代 REST API 更喜欢使用 Token。

---

比较如下：

| 项目 | Session | Token |
|------|----------|-------|
| 状态保存 | Server | Client |
| 扩展性 | 一般 | 更好 |
| REST API | 不常用 | 常用 |
| 浏览器传统网站 | 常见 | 常见 |

SG 不会深入 JWT，但知道 Session 与 Token 的区别即可。

---

# 7.78 JWT（JSON Web Token）

JWT 是目前最常见的 Token 格式之一。

例如：

```
eyJhbGciOiJIUzI1Ni...
```

JWT 通常包含：

- Header
- Payload
- Signature

其中：

Payload 保存：

- User ID
- 用户名
- 权限
- 过期时间

Signature 用于防止 Token 被篡改。

需要注意：

JWT **不是加密**。

Payload 默认可以被别人读取。

因此：

不要把密码等敏感信息直接放入 JWT。

这是很多初学者容易误解的地方。

---

# 7.79 Principle of Least Privilege（最小权限原则）（★★★★★）

前面介绍 Firewall 时已经提到过最小权限原则。

实际上：

它不仅适用于 Firewall。

更适用于所有权限管理。

例如：

财务人员：

不应该拥有：

数据库管理员权限。

开发人员：

不应该直接访问生产数据库。

普通员工：

不应该修改服务器配置。

因此：

每个人都应该：

**只拥有完成工作所需要的最低权限。**

这样即使账号被盗，攻击者能够造成的损失也会大幅降低。

---

# 7.80 Privileged Account（特权账号）

企业中通常存在一些权限非常高的账号。

例如：

- root（Linux）
- Administrator（Windows）
- Oracle SYS
- SQL Server sa
- VMware Administrator

这些账号称为：

**Privileged Account（特权账号）。**

由于它们几乎可以操作整个系统，因此必须重点保护。

常见措施包括：

- 启用 MFA。
- 禁止共享账号。
- 操作日志审计。
- 定期修改密码。
- 最少使用原则。
- 使用 PAM（Privileged Access Management）进行统一管理。

考试经常问：

为什么特权账号需要单独管理？

因为：

一旦泄露，其影响远大于普通账号。

---

# 7.81 Account 与 Identity 的区别

很多教材把 Account（账户）和 Identity（身份）混在一起介绍，其实两者并不相同。

**Identity（身份）** 指的是现实世界中的一个人。

例如：

张三。

**Account（账户）** 是系统中的登录对象。

例如：

```
zhangsan
```

一个员工可能拥有多个账户：

- Windows 登录账号。
- 邮件账号。
- VPN 账号。
- GitLab 账号。
- 数据库账号。

但这些账户都对应同一个 Identity。

现代 IAM（Identity and Access Management）系统的目标，就是统一管理这些账户，使一个 Identity 对应多个 Account，并统一进行认证、授权和审计。

---

# 第七章（续） Access Control（访问控制）与权限管理（★★★★★）

前面介绍了 Authentication（认证）和 Authorization（授权）。

接下来学习企业如何真正管理权限。

很多安全事件并不是黑客技术特别高，而是因为：

> **用户拥有了本来就不应该拥有的权限。**

因此，访问控制（Access Control）一直是信息安全管理最重要的内容之一。

---

# 7.83 Access Control（访问控制）

Access Control（访问控制）就是：

> **决定谁（Who）可以对什么资源（What）执行什么操作（How）。**

例如：

员工系统：

| 用户 | 文件 | 操作 |
|------|------|------|
| 张三 | 财务报表 | Read |
| 李四 | 财务报表 | Read / Write |
| 王五 | 财务报表 | Deny |

可以看到：

身份已经确认（Authentication）。

现在真正决定是否允许访问的是：

Access Control。

因此：

Authentication 负责：

> 证明你是谁。

Access Control 负责：

> 决定你能做什么。

---

# 7.84 Subject、Object、Permission（★★★★★）

访问控制涉及三个最基本概念。

## Subject（主体）

发起访问请求的人或程序。

例如：

- 用户
- 应用程序
- 系统服务
- API

例如：

```
Alice
```

就是 Subject。

---

## Object（客体）

被访问的资源。

例如：

- 文件
- 数据库
- 图片
- API
- 打印机
- 文件夹

例如：

```
salary.xlsx
```

就是 Object。

---

## Permission（权限）

允许执行的操作。

例如：

- Read
- Write
- Execute
- Delete
- Modify

因此一次访问控制可以表示为：

```text
Subject

↓

Permission

↓

Object
```

例如：

```text
Alice

↓

Read

↓

salary.xlsx
```

考试中经常出现：

> Subject 对 Object 拥有什么 Permission？

一定要理解这三个概念。

---

# 7.85 Access Control Matrix（访问控制矩阵）

访问控制最经典的表示方法就是：

Access Control Matrix。

例如：

| 用户 | 文件A | 文件B | 数据库 |
|------|-------|-------|--------|
| Alice | Read | Read | × |
| Bob | Read/Write | × | Read |
| Admin | All | All | All |

矩阵能够完整描述：

谁可以访问什么资源。

但是：

如果企业：

10 万员工。

100 万文件。

矩阵会非常巨大。

因此现实中很少直接使用矩阵。

而是采用 ACL 或 RBAC 等方式。

---

# 7.86 ACL（Access Control List）（★★★★★）

ACL 在 Firewall 中出现过。

文件系统中也有 ACL。

这里的 ACL 与 Firewall 思想完全一样：

> **资源记录允许哪些人访问。**

例如：

文件：

```
salary.xlsx
```

它自己的 ACL：

| 用户 | 权限 |
|------|------|
| Alice | Read |
| Bob | Read/Write |
| Admin | Full |

因此：

ACL 是：

**资源管理权限。**

谁想访问。

先查看资源自己的 ACL。

Windows 文件权限就是典型 ACL。

---

# 7.87 Capability List（能力列表）

Capability List 与 ACL 正好相反。

ACL：

资源保存：

```
谁可以访问我？
```

Capability：

用户保存：

```
我可以访问谁？
```

例如：

Alice：

```
salary.xlsx Read

mail Read

ERP Read
```

全部保存在：

Alice 自己的 Capability List。

考试偶尔会比较 ACL 和 Capability。

记住一句话：

> ACL 看资源；Capability 看用户。

---

# 7.88 DAC（Discretionary Access Control）（★★★★★）

DAC：

自主访问控制。

特点：

**资源拥有者自己决定权限。**

例如：

Windows：

你创建：

```
report.docx
```

你就是 Owner。

你决定：

- 给谁看。
- 给谁修改。
- 给谁删除。

因此：

权限由资源拥有者控制。

优点：

灵活。

缺点：

容易配置错误。

---

# 7.89 MAC（Mandatory Access Control）（★★★★★）

MAC：

强制访问控制。

与 DAC 最大区别：

> **用户不能自己修改权限。**

权限由系统统一决定。

最典型：

军队。

例如：

文件：

```
Top Secret
```

普通士兵：

即使拥有文件。

也不能把权限改成：

```
Public
```

因为：

权限由系统统一控制。

不是用户决定。

MAC：

安全性最高。

灵活性最低。

---

# 7.90 RBAC（Role-Based Access Control）（★★★★★）

现代企业使用最多的是：

RBAC。

Role：

角色。

不是：

用户。

例如：

公司：

```
Alice
Bob
Tom
```

不是直接配置权限。

而是：

```
经理

财务

开发

人事
```

权限赋予：

角色。

用户加入：

角色。

例如：

```text
Alice

↓

财务

↓

ERP Read
工资系统 Write
```

如果：

Alice 调岗。

只需要：

移出：

财务。

加入：

人事。

无需重新配置所有权限。

因此：

RBAC 非常适合大型企业。

---

# 7.91 RBAC 为什么最常用？

假设：

企业：

5000 名员工。

100 个系统。

如果：

每个人直接配置权限。

管理员几乎无法维护。

RBAC：

变成：

```text
用户

↓

角色

↓

权限
```

例如：

1000 人都是：

销售。

他们共享：

销售角色。

以后：

销售角色增加：

CRM 导出权限。

1000 人：

自动获得。

管理成本极低。

因此：

几乎所有大型企业都采用 RBAC。

---

# 7.92 RBAC 示例

例如：

公司存在三个角色。

| Role | 权限 |
|------|------|
| HR | 员工信息 |
| Finance | 工资系统 |
| IT | 服务器管理 |

员工：

| 用户 | Role |
|------|------|
| Alice | HR |
| Bob | Finance |
| Tom | IT |

以后：

Tom 离职。

Jerry 入职。

管理员：

无需重新配置服务器权限。

只需要：

```text
Jerry

↓

IT Role
```

全部权限立即继承。

---

# 7.93 ABAC（Attribute-Based Access Control）

近年来越来越多企业开始使用：

ABAC。

Attribute：

属性。

ABAC 不仅看角色。

还会看很多属性。

例如：

- 部门。
- 时间。
- 地点。
- IP。
- 国家。
- 设备类型。
- 登录风险。
- 是否 VPN。
- 是否公司电脑。

例如：

规则：

```
财务部门

并且

公司电脑

并且

东京办公室

并且

工作时间

允许访问 ERP。
```

任何一个条件不满足。

拒绝。

因此：

ABAC 比 RBAC 更灵活。

---

# 7.94 RBAC 与 ABAC 对比（★★★★★）

| 项目 | RBAC | ABAC |
|------|------|------|
| 判断依据 | Role | Attribute |
| 灵活性 | 高 | 更高 |
| 管理难度 | 较低 | 较高 |
| 企业应用 | 非常广泛 | 越来越多 |

SG 一般了解即可。

重点仍然是 RBAC。

---

# 7.95 Principle of Separation of Duties（职责分离）（★★★★★）

职责分离（Separation of Duties，SoD）是企业权限管理的重要原则。

它强调：

> **不要让同一个人同时拥有互相制约的权限。**

例如：

采购流程：

```
申请

↓

审批

↓

付款
```

如果：

一个人：

全部完成。

那么：

他可以：

自己申请。

自己审批。

自己付款。

几乎没有监督。

因此：

企业通常规定：

| 工作 | 人员 |
|------|------|
| 提交申请 | A |
| 审批 | B |
| 财务付款 | C |

这样可以有效防止舞弊。

银行、证券、保险等金融行业尤其重视职责分离。

---

# 7.96 Need to Know（按需知悉原则）（★★★★★）

Need to Know 指：

> **只让员工知道完成工作所必须知道的信息。**

例如：

客服：

可以查看：

客户姓名。

联系方式。

订单。

但是：

不能查看：

银行卡密码。

身份证照片。

后台数据库。

因为：

这些信息不是完成工作必须知道的。

Need to Know 与 Least Privilege 十分相似。

区别在于：

- Least Privilege 更强调"权限"。
- Need to Know 更强调"信息"。

二者经常一起出现。

---

# 7.97 Least Privilege 与 Need to Know 的区别（★★★★★）

很多教材会一起介绍这两个原则。

可以这样理解：

| 原则 | 控制对象 | 示例 |
|------|----------|------|
| Least Privilege | 操作权限 | 不能删除数据库 |
| Need to Know | 信息访问 | 不能查看工资信息 |

实际企业中，两者通常同时实施。

例如：

普通员工：

- 没有修改工资数据的权限（Least Privilege）。
- 看不到其他员工工资（Need to Know）。

这样既限制了操作能力，也限制了信息获取范围。

# 第七章（续） AAA、IAM 与企业权限管理（★★★★★）

前面介绍了 Authentication（认证）、Authorization（授权）和 Access Control（访问控制）。

接下来学习企业权限管理最核心的一套体系——AAA。

几乎所有大型企业、Active Directory、VPN、云平台都会使用 AAA 思想。

---

# 7.99 AAA（Authentication、Authorization、Accounting）（★★★★★）

AAA 不是一种产品，也不是一种协议，而是一种安全管理模型。

AAA 由三个部分组成：

| 缩写 | 全称 | 中文 |
|------|------|------|
| A | Authentication | 身份认证 |
| A | Authorization | 授权 |
| A | Accounting | 审计 / 计费 |

企业用户登录时，一般都会经历 AAA。

整个流程如下：

```text
用户登录
      │
      ▼
Authentication
（确认身份）
      │
      ▼
Authorization
（确认权限）
      │
      ▼
允许访问资源
      │
      ▼
Accounting
（记录日志）
```

因此：

AAA 实际上就是企业身份管理的完整流程。

---

# 7.100 Authentication（认证）

Authentication 前面已经介绍过。

它回答的问题只有一个：

> 这个用户是谁？

例如：

员工输入：

```
用户名

密码

MFA
```

系统验证成功。

说明：

身份正确。

但是：

现在仍然不知道：

他有没有权限。

所以进入下一步。

---

# 7.101 Authorization（授权）

认证成功后。

系统继续查询：

```
Role

Group

ACL

RBAC
```

决定：

员工能够访问哪些资源。

例如：

开发人员：

可以：

```
GitLab

Jira
```

不能：

```
工资系统
```

因此：

Authorization 决定的是：

访问范围。

---

# 7.102 Accounting（★★★★★）

很多同学第一次看到 Accounting 会认为：

就是财务。

实际上：

AAA 中的 Accounting 更准确理解为：

> **记录用户做了什么。**

例如：

日志：

```text
2026-07-26

Alice

Login

Success
```

或者：

```text
Bob

Delete File

Success
```

或者：

```text
Tom

VPN Connected

3 Hours
```

这些都是：

Accounting。

因此：

Accounting 包括：

- 登录时间。
- 登出时间。
- 登录 IP。
- 使用时长。
- 操作日志。
- 数据流量。
- 命令记录。

很多 VPN、Radius、TACACS+ 都会保存这些信息。

考试经常问：

AAA 中负责记录日志的是哪一个？

答案：

Accounting。

---

# 7.103 为什么需要 Accounting？

很多安全事件发生后。

管理员最想知道：

```
谁？

什么时候？

登录哪里？

做了什么？

删除了哪些文件？
```

如果没有日志。

根本无法调查。

因此：

Accounting 既服务于：

安全审计。

也服务于：

事故调查（Forensics）。

---

# 7.104 AAA 总结（★★★★★）

一句话记忆：

Authentication：

> 你是谁？

Authorization：

> 你能做什么？

Accounting：

> 你做了什么？

考试中几乎每年都会考这一组概念。

---

# 7.105 IAM（Identity and Access Management）（★★★★★）

现代企业通常不会分别管理：

- Windows 用户。
- 邮件用户。
- VPN 用户。
- ERP 用户。
- GitLab 用户。

因为：

员工可能拥有几十个账号。

管理成本非常高。

于是出现：

IAM。

Identity and Access Management。

中文：

身份与访问管理。

IAM 可以理解为：

> **统一管理企业所有身份和权限的平台。**

---

# 7.106 IAM 能做什么？

IAM 一般负责：

- 创建账号。
- 删除账号。
- 修改密码。
- 分配角色。
- 回收权限。
- SSO。
- MFA。
- 审计日志。
- 生命周期管理。

例如：

员工入职。

HR：

录入：

```
Alice
```

IAM：

自动：

- 创建 Windows。
- 创建邮件。
- 创建 VPN。
- 创建 ERP。
- 创建 Teams。
- 创建 GitLab。

整个过程：

无需管理员逐个操作。

---

# 7.107 Joiner、Mover、Leaver（★★★★★）

IAM 最重要的管理对象就是：

员工生命周期。

通常称为：

JML。

---

## Joiner

新员工入职。

自动：

- 创建账号。
- 分配角色。
- 分配邮箱。
- 分配 VPN。
- 分配办公系统。

---

## Mover

员工调岗。

例如：

开发。

↓

项目经理。

IAM：

自动：

删除：

开发权限。

增加：

项目管理权限。

无需重新创建账号。

---

## Leaver

员工离职。

IAM：

立即：

- 禁用账号。
- 删除 VPN。
- 删除邮箱。
- 回收权限。
- 回收许可证。

如果离职员工账号没有关闭。

攻击者可能继续登录企业系统。

因此：

Leaver 是企业审计重点。

---

# 7.108 Provisioning（账号开通）

Provisioning：

账号开通。

例如：

员工加入：

IT 部门。

IAM：

自动：

```text
Windows

Office365

GitLab

Jira

VPN
```

全部创建完成。

称为：

Provisioning。

---

# 7.109 De-provisioning（账号回收）

与 Provisioning 对应：

De-provisioning。

例如：

员工离职。

IAM：

自动：

- 禁用账号。
- 删除权限。
- 删除角色。
- 删除 Token。
- 回收 License。

企业最怕：

"离职半年账号还存在。"

这是很多真实安全事件发生的重要原因。

---

# 7.110 Group（组）

大型企业几乎不会：

一个用户。

一个用户配置权限。

而是：

Group。

例如：

```
Finance

HR

Sales

Developer
```

权限赋予：

Group。

员工加入：

Group。

自动获得权限。

实际上：

---

# 7.111 Permission Review（权限审查）（★★★★★）

很多员工：

几年后：

岗位变化。

权限越来越多。

例如：

原来：

开发。

后来：

测试。

后来：

经理。

后来：

架构师。

如果旧权限一直保留。

就会出现：

权限膨胀（Privilege Creep）。

因此企业需要：

定期进行：

Permission Review。

例如：

每半年：

部门经理确认：

```
Alice

是否仍需要：

Database Admin？
```

如果：

不需要。

立即删除。

---

# 7.112 Privilege Creep（权限膨胀）

Privilege Creep：

随着时间推移。

员工权限越来越多。

但旧权限没有删除。

例如：

```
开发权限

+

测试权限

+

管理员权限

+

运维权限
```

全部保留。

最终：

任何系统都能访问。

风险极高。

IAM 的重要目标之一就是：

防止：

Privilege Creep。

---

# 7.113 Orphan Account（孤儿账号）

Orphan Account：

已经没有负责人。

但账号仍然存在。

例如：

员工：

离职。

账号：

没有删除。

或者：

供应商结束合作。

VPN：

仍然有效。

攻击者如果获得：

Orphan Account。

几乎不会被发现。

因此：

企业必须：

定期清理：

- 离职账号。
- 测试账号。
- 临时账号。
- 默认账号。

---

# 7.114 Shared Account（共享账号）

很多公司以前喜欢：

```
admin

admin123
```

所有管理员：

共同使用。

这种做法：

风险极高。

因为：

出了事故。

无法判断：

到底是谁操作。

因此现代企业强调：

> **One Person, One Account（一个人，一个账号）。**

共享账号：

应尽量避免。

如果必须使用。

必须：

记录操作日志。

使用 PAM。

# 7.116 Directory Service（目录服务）（★★★★★）

如果一个公司只有 10 名员工。

那么：

账号完全可以人工管理。

但是：

如果公司有：

- 3000 名员工
- 500 台服务器
- 200 个业务系统

那么管理员几乎无法手动维护每个账号。

于是企业引入：

**Directory Service（目录服务）。**

目录服务就是：

> **集中保存所有用户、计算机、组织、组以及权限信息的数据库。**

例如：

```text
公司

├── IT部门
│     ├── Alice
│     ├── Bob
│
├── 财务部
│     ├── Tom
│
├── 人事部
│     ├── Lisa
```

所有账号统一保存在目录服务器。

整个企业共享同一份身份信息。

---

# 7.117 LDAP（★★★★★）

LDAP（Lightweight Directory Access Protocol）

中文：

轻量级目录访问协议。

LDAP 不是数据库。

也不是操作系统。

它是一种：

> **访问目录服务的协议。**

可以理解为：

```text
HTTP

↓

访问网页

LDAP

↓

访问目录服务
```

例如：

员工登录电脑。

电脑：

向 LDAP 查询：

```
Alice 是否存在？

密码是否正确？

属于哪个部门？

属于哪些 Group？
```

LDAP 返回结果。

系统再决定是否允许登录。

因此：

LDAP 的作用就是：

**访问目录服务器。**

# 7.118 Active Directory（AD）（★★★★★）

Microsoft 最著名的目录服务就是：

简称：

AD。

- Computer
- Printer

```
↓

↓

VPN

Mail

Windows Login
```

这些信息都统一保存在 AD 中。

所以：

员工换电脑以后。

# 7.119 Domain（域）

加入：

管理员就可以：

统一：

PAM：

自动：

修改：

root 密码。

即使有人偷偷记住。

也无法再次登录。

---

③ 会话录像（Session Recording）

管理员登录服务器后：

所有操作：

全部录像。

例如：

```
rm -rf

shutdown

userdel
```

全部保存。

以后：

发生事故。

可以：

回放整个操作过程。

---

④ 审批流程

管理员：

不能随便：

登录服务器。

例如：

需要：

经理审批。

批准以后。

PAM：

才允许登录。

---

⑤ 临时授权（Just-in-Time Access）

现代企业越来越流行：

JIT（Just-in-Time）。

管理员：

平时：

没有管理员权限。

真正需要维护时。

申请：

30 分钟。

系统：

自动：

开放权限。

30 分钟结束。

自动：

收回权限。

这样：

管理员账号长期处于高权限的风险大大降低。

---

# 7.131 Bastion Host（堡垒机）（★★★★★）

国内经常称：

堡垒机。

英文：

Bastion Host。

很多教材：

容易把 PAM 与堡垒机混在一起。

实际上：

堡垒机强调：

**统一入口。**

例如：

管理员不能：

直接 SSH：

Linux。

必须：

先登录：

```
Bastion Host

↓

Linux
```

这样：

所有登录：

全部经过堡垒机。

方便：

- 审计
- 录像
- 权限控制
- MFA
- 操作记录

现代企业很多 PAM 产品本身就集成了堡垒机功能。
